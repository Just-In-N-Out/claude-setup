# Parallel features

Moved out of feature-dispatch `SKILL.md` on 2026-10-23 to keep it under Hermes' 100,000-character skill limit. Load it whenever two or more features are planned, building or reviewing at the same time.

- Run at most six builders/finishers at once (Justin raised the cap from three to six). This is a ceiling, not a concurrency target: require separate source/test ownership or explicit sequenced boundaries and available disk. APFS free space swings by tens of GB as purgeable space and snapshots are reclaimed, so re-run `df -h ~` immediately before turning low disk into a question for Justin; prefer dispatching with a stop threshold in the brief (commit what passes and stop below ~1.5 GiB, never delete anything) over holding approved work. Stagger heavy Chrome/corpus/performance gates independently of builder count; planners may investigate read-only in parallel. Count current builder roles from the live list before filling a slot. Approve waiting plans and prepare their briefs immediately, but keep them `queued` with a named slot/dependency condition instead of exceeding six concurrent builders/finishers. On every builder completion, classify the actual result first: `ready-for-review` advances to fresh review; a source-restored or policy-blocked branch does not. Record the hold and remove its stale active agent immediately, then fill the freed builder slot with eligible approved work in the same turn when safe. Compare planned writes with each sibling's complete committed/dirty/untracked path union. Through `terminal`, collect `git diff --no-renames --name-only -z <base>...HEAD`, `git diff --no-renames --name-only -z HEAD`, and `git ls-files --others --exclude-standard -z`; intersect sets programmatically. For record-only overlaps, exclude shared records from the builder, collect private drafts, and assign their edits to a coordinated finisher; record this boundary in plan/brief/board before launch. Keep Docs & records outstanding, not waived. Queue unresolved source/test overlap.
- **A queued feature waiting only on a sibling's merge** can fill an idle builder slot early when its plan permits parallel building and neither the plans' Touches nor the sibling's actual `git diff --name-only main...` share a source or test file. Build from current main, and write the merge order into its brief and board note: it merges after the sibling, and its finisher rebases onto the sibling and regenerates same-base before/after and probes before merging. Shared outputs (the same corpus pastes) still need that rebased proof; unresolved source/test overlaps still mean waiting. Record-only overlaps may use the coordinated-finisher boundary above.
- Treat browser/corpus capacity separately from source ownership. Independent branches can still compete for the same Chrome instance, network fonts and host performance budgets. Stagger expensive gates where practical, preserve failed raw runs and repeat unchanged source before diagnosing a load-dependent failure; never relax thresholds or declare a flake fixed from an isolated pass.
- Each builder works in its own worktree. The project's merge lock and rebase loop handle main moving.
- **"What's running?" / "status?"**:
  - read the board for the requested scope;
  - call `delegate_task(action="list")` for each named agent's live status, actual model and transcript path;
  - for a builder, `git -C <worktree> log --oneline main..HEAD` shows accumulated branch commits, not necessarily work by the current run. A missing worktree during context loading is not proof the agent stopped;
  - if Justin asks whether a role has stopped, repeats the status question, or a long-running role has no visible result, take one bounded snapshot of the latest transcript activity/result and any named plan artifact. Distinguish **listed running** from **recent progress observed**; an alive task wrapper or elapsed time alone does not prove useful progress. Report stale or uncertain activity plainly, inspect an evidenced blocker through the recovery procedure, and do not invent an ETA, quota failure or replacement owner.

  For **"did you start the planner?"**, answer yes/no first, then its actual model and verified live state; do not dump the whole board. Treat **"wait, is the planner stopped?"** as a status question, not an instruction to stop it. Give a feature-wide status one short line per feature: name, phase and concrete progress. `/agents` shows live agents too.
- **Reconcile session-local liveness with shared ownership before dispatch.** Read the shared board and the local delegate list together. An active board entry absent from this session's list may belong to another desktop or messaging session; absence is not a dead-owner signal. Check its plan and actual branch diff before assigning overlapping files, and preserve unrelated authorized work. Report locally verified live agents separately from other-session activity whose liveness is not yet verified; do not restart those agents or rewrite their board rows merely to reconcile counts. Key shared handoff sections by feature and owning session so a selection in one chat does not appear to cancel another chat's assignment. Re-read current anchors before editing shared notes; if they changed, merge a targeted patch rather than replacing the file from an older snapshot. Steer the current planner with newly discovered sibling ownership and request overlap findings; independent read-only planning need not wait for build sequencing. Treat profile-wide routing overrides as shared state too: minimize the set → dispatch → reset interval and verify the returned child's model before reporting it.
- **Distinguish visibility, liveness and communication across chats.** Answer the requested scope from the cheapest authoritative view first: session metadata identifies the chat; the shared board records its last pipeline position; a live owner registry establishes an open owning runtime; worker activity requires that worker's live status or recent activity; a direct acknowledgment requires an actual reply. Do not label a board note or an open desktop chat as live confirmation from its orchestrator. When asked to test communication, try one documented, owner-authorized route and report the observed result, not a speculative capability claim. A saved shared note is not delivered or read until acknowledged. A route refusal neither proves universal messaging is impossible nor authorizes taking over the session, restarting the app or bypassing its ownership boundary. Keep cross-chat status replies to one plain-language line per feature, labelled as recorded or live-observed.
- **Count live agents, not board rows.** For a quick count ("how many running, how many queued?"), call `delegate_task(action="list")` and answer with counts in the headings (`🟢 Running (N)`, `⏳ Queued (N)`, `⏸ Blocked (N)`), one short line per feature with role and model/effort, then the latest verified build and usage; do not dump the whole board. When Justin quotes a reminder containing more rows, explicitly separate running agents from queued tasks and stopped tasks so the row count cannot be mistaken for concurrency. Put queued work in a separate section; branch-only commit counts describe accumulated branch work, not commits made by the current finisher. Use the live agent's `running_seconds` for its current run; label a board's time-in-phase separately when a retry kept the original phase timestamp. An automatic script report is a timestamped board snapshot, not independent proof of liveness; reconcile it with the live list and report discrepancies rather than silently treating queued or finished work as running. If a child disappears before its completion arrives, say the result is pending—absence alone proves neither success nor failure.
- **No windows open on the Mac.** Agents run inside the Hermes gateway process. If Justin wants to watch one, open a Terminal window for him with `osascript` that tails its transcript (`tail -f <transcript path>`).
- **Status ping and re-ask reminders:** two no-agent cron jobs post every open feature every 10 min (Justin's interval), and re-ask an unanswered plan or question every 2 min (at most 5 times). For their job IDs, the pause/resume/retime commands, and the board fields the scripts read, see `references/status-pings.md`, which also holds both message formats. Keep them terse: Justin finds wordy pings noise.
- **Paste check numbers collide.** Parallel builders each take the next free HANDOFF paste check number, so several pick the same one. Every time a merge report names its paste check, steer each live builder and finisher of the same project in that turn: "<feature> merged as <BUILD> and took <check>; use the next free number on main at merge, everywhere". Put "take the next free number on main at merge time" in every builder and finisher brief instead of a fixed number.
