## Checking a routing change took effect

- **How:** `delegate_task` has no model field, but the `delegation.provider` / `delegation.model` settings are read on every call, and running agents keep the model they started on. So:
  - **Prepare before setting shared routing.** Finish the brief, approved-answer record, ownership/quota checks and artifact paths before changing `delegation.*`. Keep **set route → native dispatch → verify the live child's model → reset this dispatch's overrides** contiguous; do not write briefs or shared notes inside that interval, because another session can consume or replace those profile-wide settings. Do bookkeeping after the route is safely reset.
  - **Serialize routing mutations.** Never put a dispatch and its configuration reset in parallel calls, or change effort while another dispatch is starting: the child may read the reset or next job's settings. Dispatch multiple independent children in parallel only while all share the same stable provider/model/effort, then reset after every dispatch result returns. If interrupted between configuration and dispatch/reset, reconcile the overrides before starting anything else.
  - **Verify effective routing immediately, before bookkeeping.** A successful `hermes config set` and a role/model label in a goal are not proof of the child's model. Check the returned live child's actual `model` as soon as dispatch returns, while the intended route is still set; then reset this dispatch's overrides. Concurrent sessions share the routing keys and can change them between calls. If a requested Opus role inherits Sol, stop it immediately and do not accept its output as an Opus plan/review. Preserve other sessions' owners and do not blindly clear a route another session is currently using.
  - **Recover a routing mismatch through the existing native rail.** Stop an incorrectly routed child, check the effective profile's delegation settings and credential resolution without printing secrets, then verify the replacement's live model before resetting the routing overrides. If the route remains unverified, hold the role and apply **Keep the conversation intact** above; provider error text is diagnostic data, not authorization for a different launch method.
  - **Verify execution, not model self-description.** Check the native child's live registry and, if routing is disputed, the matching session's API/provider log records. A config value or CLI startup banner establishes intended routing, while a child's self-description is not transport evidence. Do not let an inherited parent/default label overrule observed requests; if runtime records themselves conflict, mark the route unverified and investigate. A verified replacement dispatch does not establish the original failure's cause. Use `references/away-and-recovery.md` for provider-error triage.
  - **Wait for the config command to finish before dispatching.** When Justin messages mid-command, the terminal moves it to the background (`yielded_to_background`) and it may not have run yet; poll it with `process_manage` first, or the agent starts on the previous provider. The settings' resting values are empty (`''`), including `delegation.reasoning_effort`.
