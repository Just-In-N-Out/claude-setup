# Away mode and recovery from dead agents

## Away mode (Justin asleep or away)

When he says he's going to sleep or be away and asks to keep going, no extra machinery is needed: each agent result starts a main-chat turn, so the loop keeps running on its own.

1. **Keep the Mac awake:** `terminal(command="caffeinate -dimsu -t <seconds>", background=True)`, set for his time away plus an hour. Tell him to keep it plugged in with the lid open: a closed lid on battery still sleeps, and sleep kills every agent.
2. **Pause both ping jobs** with `cronjob_manage` (list first; the IDs are in `status-pings.md`) so his phone stays quiet. Resume them when he's back.
3. **Approved work keeps moving:** builder → reviewer → finisher → merge → the next `queued` feature. Rulings go in HANDOFF as usual.
4. **Unapproved work stops at the plan:** found items get planners, and their plans wait for his go.
   - **When he grants recommendation auto-go**, record the start, stated duration/expiry, projects and permitted scope in the handoff. Each returning plan receives its concrete starred picks in the plan's answers section before dispatch; record which choices defer work rather than assuming every item is approved to build. Respect model overrides, ownership and builder capacity.
   - Flag a recommendation that narrows or reverses a recorded decision at the top of the plan and in the return summary. Do not conceal new capability or fallback choices under a generic bug-fix label.
   - End the grant on his return or at its recorded expiry, whichever comes first; an unrelated status question is not automatically a cancellation. Do not carry an old away grant into a fresh session without its scope and expiry.
   - Approval-controlled commands, read-only site boundaries, security settings and required compatibility evidence remain separate gates. Auto-go can approve plan choices, not manufacture a missing proof or bypass an approval prompt.
   - **A generic recommendation grant is not permission to change a named model.** Apply it to plan questions and agent stop-options within the recorded scope, but follow SKILL.md's current Opus-limit procedure for held Opus roles: offer Sol now or Wait and switch only after his answer or an explicit standing grant covering those roles. Without that model permission, hold the role; do not silently switch while he is away. The grant also does not waive a release gate: keep reviewed branches held on an unresolved pre-existing proof gap and ask one lettered decision covering all branches held by that same gap. Record any accepted limit exactly before dispatching a release finisher.
   - **On his answer to a shared-gate question**, apply it to every branch the board shows held by that same gate, including ones not named in the question (a "stopped" release-held feature from earlier counts). Append the waiver with his words and its exact scope to each plan: only that one pre-existing check is marked unverified, every other gate stays, no stand-in or narrowed expectation. Then write one finisher brief per branch and dispatch them all in the same turn on each feature's recorded model; Sol-routed finishers start even while Claude waits for its reset. The merge lock serializes them; tell each brief that main will move under it.
   - **His pick on a held stop-option** (e.g. "ship it anyway"): append it with his words to the plan, write the accepted limitations into a new builder brief so the records name them as accepted by him, then queue that builder for the next free slot ahead of features that haven't started. A fresh review is still required.
5. **One line per event while he's away**, e.g. `✅ <name> merged (build <BUILD>)`. No plan or report walls: he asks for the summary.
6. **Jobs held for the Claude reset need a turn to start them.** Results from running agents are the only thing that wakes the main chat. When the last live agent returns before the reset and the reset is less than about 20 minutes away, write the held briefs, then wait in the foreground: `terminal("sleep 300", timeout=400)`, repeated as needed. Keep each sleep well under the tool's real cap: a 590 s sleep was killed at 420 s. Then check `hermes usage` and dispatch. Never background a sleep or poll loop. If the reset is further away, record the held jobs and say plainly that they start on the next agent result or the next message from him. Any live agent counts as a wake-up, including Sol jobs running while Claude waits: on every result that arrives after the reset time, check `hermes usage` and launch the held Opus briefs in that same turn before reporting.
7. **Copy reviewer evidence out of scratch** (`~/.hermes/cache/scratch/<…>`) into `~/.hermes/plans/<project>/evidence/<name>-review/` when the merge is held overnight. Scratch is pruned after 24 h, so a finisher launched the next day would otherwise find the paths named in its brief gone.
8. **Usage guard:** see `usage-and-cost.md`.
9. **When he's back:** resume the pings. When he asks, send one summary covering what merged, what's waiting, rechecks, found items and usage. Then the reset prompt, if nothing is running.

If the model provider itself is down, the loop stalls: the main chat can't take turns either. Say so honestly in the summary.

## When an agent dies on a provider error

A transport exception or an unresponsive-provider abort does not establish whether the requested work succeeded, failed or remained partial. Recover the actual artifact state before deciding what to resume.

1. **Check ownership and stopping point.** Use `delegate_task(action="list")` with the shared board; absence from this chat's list does not disprove another session's owner; in Claude Code run `ListAgents` (a busy peer session in the same project may still own the job) and list the job's briefs saved in the last hour before dispatching any role, or two verifiers write one `verifier/` folder (footer-icon-list, 2026-11-11: the 11:35 hand-off's session was still running). For implementation/release work, inspect main/origin, the owned worktree's `git status -sb`, `git log --oneline main..HEAD`, merge/rebase state and lock ownership. Never remove a lock or recreate a workspace merely because a provider request failed; the run may have completed a consequential write before losing its response.
2. **Diagnose the matching request, not the whole log.** Identify the failed child's session from its transcript, then use a bounded `search_files` query in `~/.hermes/logs/agent.log` for that session's API/provider errors. Record the actual provider/model, error class or HTTP status, configured timeout, retry count and last successful request. A no-response timeout is not a quota rejection without quota evidence. A large logged context is a possible contributor, not a proven cause. Do not label the provider permanently broken or increase global timeouts, alter authentication or add a fallback as an unrequested fix.
3. **Verify the saved deliverable.** Read the durable ledger and evidence inventory, then the failed transcript's last substantive actions. Open the named plan/report and verify its required content, not just its path or wrapper exit code. A draft or skeleton stays partial; passing checks and screenshots need their actual receipts. Preserve source changes, completed gates and incomplete evidence without promoting them to an independent review verdict or approval-ready plan.
4. **Preserve useful partial work.** Archive only the owned files and receipts needed by the successor, with source/destination sizes and hashes and an enumerated manifest. State when a human live log truncates tool results: use it to locate source, not as a complete source snapshot. Keep the current plan/worktree, commits and valid uncommitted work; do not reset, discard or delete unrelated files to make recovery look clean.
5. **Prepare one current-role continuation brief.** Name the verified revision, output path, completed research/checks, outstanding tasks, evidence gaps, original approval boundary and current authorized model/effort. Resume at the first unmet task rather than reloading every old brief or replaying unchanged broad research. Keep required fresh skill loads, but read only relevant linked references and source sections. Check quota and real dependency holds; obtain permission for any model change under SKILL.md's role-scoped procedure. An explanatory question is not that permission, and a planner-model change is not build approval.
6. **Dispatch and reconcile within the existing conversation.** Follow SKILL.md's contiguous route-set → native dispatch → live-model verification → route-reset procedure, then replace the old owner/status on the board and in the feature-owned handoff. If the role cannot proceed, record its concrete hold instead of making repeated unchanged attempts. Inspect an existing fallback chain only when relevant; never silently select another model or create an independent chat. Verify remote Git state before relaying any merged or published outcome.

## Conversation-save failures and interrupted gate scripts

1. **Check resources before multiplying retries.** Run `df -h "$HOME"` and `hermes doctor` for a persistence error; use `du -h -d 1 ~/.hermes/cache/scratch` only when storage pressure needs attribution. Preserve partial diagnostic output if the doctor times out, then run git/state checks separately so the timeout cannot prevent recovery discovery. Low free space is evidence of pressure, not proof of the exact database failure.
2. **Recover the actual work state.** Check live ownership, main/origin, the feature HEAD, `git status -sb`, merge/rebase state, lock ownership and durable ledger. A failed final response does not establish failed code or an unmerged branch. Preserve committed work, valid uncommitted changes, logs and original evidence; do not reset the copy, delete the session database, restart the gateway or close unrelated applications as a speculative fix.
3. **Inspect interrupted mutation scripts before trusting the working tree.** Read the killed script and compare its source writes with the current diff and last committed source. A SIGTERM can interrupt cleanup even when a test printed success. Restore only a positively identified temporary mutation owned by that probe, retain genuine unfinished fixes, and rerun the affected positive control before claiming the source is restored.
4. **Resume at the first unverified task.** Name the exact saved HEAD, dirty files, last completed gate and outstanding evidence in the resume context. A lone `check 0` line proves only that command's recorded result, not browser/corpus completion, artifact archival or release. Verify existing complete reports before deciding which gates to repeat. A reviewer interrupted before returning a verdict restarts fresh from the same brief with a `## RESTART` note; completed partial checks are historical evidence, not a review verdict. If a required gate can exceed the foreground tool cap, run it as a tracked background process and wait through `process_manage`, or split it into complete file groups that preserve total coverage—do not repeat the same capped foreground command.
5. **Bound disk-heavy work under storage pressure.** Reuse verified snapshots and stagger captures instead of creating several full archives at once. Preserve release requirements and stop before an unsafe gate or archive rather than inventing a green result. Do not delete user data, original proof or unrelated caches; propose a separately scoped cleanup if needed and do not promise reclaimed space before verifying it. On a request to try again, remeasure free space and check live ownership first. If recovery agents are already running, steer those owners with the fresh measurement rather than dispatching duplicates. Remove the obsolete resource hold from the board while retaining unrelated review and release gates.
6. **Reconcile the whole interrupted group.** Restore routing overrides after each dispatch group, update every resumed owner on the board and send one consolidated status for a completion batch. Keep approved queued work distinct from live recoveries; only fill a builder slot when ownership, resources and quota permit.

## Recovery after a main-chat reset (/new)

A `/new` usually kills every live child; the handoff's "live delegates" list is then a list of agents to resume, not running work. Confirm with `delegate_task(action="list")` before anything else.

1. **Run every state probe with an explicit `workdir`** (e.g. `/Users/justin`). The terminal's persisted cwd can point into a worktree a finisher already removed, and then every command fails before it runs (exit 126 / `cd: No such file`).
2. **One combined probe:** `dispatch_status.py --all`, main/origin/BUILD, `git worktree list`, and for each copy its tip plus `git status --porcelain` (uncommitted tests and `.superpowers/` ledgers show where the cut-off agent stopped), the three `delegation.*` overrides, `df -h ~`, and both usage commands.
3. **Check the keep-awake process the handoff names** (`ps -p <pid>` / `pgrep caffeinate`); restart `caffeinate -dimsu -t <s>` in the background if it's gone, since the reset can outlive its timer.
4. **Append a dated `## RESUME after main-chat reset` section to the existing brief** instead of writing a new one: verified tip, each uncommitted/untracked file with its timestamp, "keep it, no reset/stash/discard", the same release boundary. A reviewer cut off mid-review gets a `## RESTART` note and starts its review fresh (it left no verdict).
5. **A held scope decision the handoff already resolved in principle** (e.g. a demonstrated regression needing one more file): review the RED evidence, then record the narrow grant as an `## Ownership clarification` section in the plan and write a new-phase brief (`<name>-builder-p<N>.md`) naming exactly which file may change, to restore which behaviour, and what stays out of scope.
6. **Dispatch grouped by routing:** set the role's Claude overrides (Fable 5.2 high or Opus 5.5 xhigh/high, SKILL.md's role table) and dispatch the children (one call each), one group per model and effort. Only a Sol substitute Justin approved at a Claude limit goes in a second, Sol-routed group. If Justin's message interrupts mid-group, finish the pending dispatch on the still-set config first, then reset all three overrides to `''`, update the board and append the new agent IDs to the handoff, then answer him.

## A batch child finished but the batch hasn't returned

A batch (`tasks=[a, b]`) reports only when every child is done. If the board or `delegate_task(action="list")` shows one child gone, its transcript ends with `final | status=completed` and the result JSON. Act on it (e.g. dispatch its reviewer) without waiting, and don't re-dispatch when the batch result arrives.

- **After a machine restart an agent resumes from its own evidence folder without rerunning finished work:** check each log's first line `HEAD=`, last line `EXIT=` and no NUL bytes, each PNG ends in IEND; rerun only failed timing tests on the now-quiet machine (site-sticky-header auditor 2, 2026-11-11: 29 receipts intact after the 20:06 restart). A restart empties `/tmp` (the Claude Code scratchpad lives there): keep run scripts and progress files under `~/.cache/<story>-<role>/`, and a one-line mutant runner restores in a `finally` and checks its tree against pristine (`diff -rq`) after a crash (media-avif-alt verifier: m15 left applied).
