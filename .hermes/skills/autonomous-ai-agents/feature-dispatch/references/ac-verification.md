# AC verification: verifier, blind auditor, ac-check

Justin, 2026-10-23: the orchestrator confirms every acceptance criterion (AC) is met before the finish step, without doing a lot of work itself. Two independent agents prove each AC with receipts, and one script compares them. Applies to Full and Mini, every repo.

## Why

A single verifier can be wrong. Accepting an unmet AC ships a broken feature; rejecting a met one only costs a round, and the no-progress rule already catches that. Four layers close the dangerous direction:

1. **Receipts:** each accepted AC names its test, a log stamped with the commit it ran on, and a screenshot. The log must show that test's own pass line, with no fail or skip line for it.
2. **Old-code check:** the same test must fail on the base commit (or fail to build against it). A test that passes on both doesn't test the AC.
3. **Blind second opinion:** when the verifier says clean, a fresh AC auditor that never sees the verifier's report or receipts proves every AC again. Any disagreement means not accepted.
4. **Reviewed head:** `--reviews` refuses a head with commits no clean review covers (`review-loop.md`); a pure rebase of the reviewed head counts as covered.

After the finisher's pure rebase, a **rebase receipt** (step 5 below) reruns every AC's test on the new head, so the two reports for the head they proved still count (2026-11-10): no new verifier or auditor.

## At "go"

The orchestrator makes a read-only copy of the approved plan, which `ac-check.sh` reads from then on, so a later edit can't add ACs or `(live)` tags:

```
mkdir -p <evidence> && install -m 444 <plan> <evidence>/plan-approved.md
```

When Justin decides something mid-build that changes an approved AC, a planner amends the plan, dispatched after the fix round it describes has landed (written during a round it is ahead of head: hold the install and re-read against the fixer's head its marked clauses, its status words ("fixer N is at work") and its receipts sorter grep, which a fix done another way than predicted leaves constant across heads, site-slider amendments 4 and 7–10) and working under its own `~/.cache/<job>-<role>/` (every agent shares the session scratchpad, where generic names like `amend.py` get overwritten; build the folder from the job's full name, not its initials: staging-fit-capture and staging-fit-cancels both gave `sfc-a`, and a later auditor wrote into the earlier one's folder). Before the verifier runs, grep the story's HANDOFF section for the builder's own rulings ("builder's ruling", "not yet confirmed") and set each against the AC lines: a ruling that changes what an AC states needs a fix or an amendment first, because the AC's own test already asserts the changed behaviour and stays green (site-native-structure AC6, 2026-11-09). It marks each changed line, adds an Amendments list at the top, names every earlier receipt that still encodes the old expectation (and the difference now expected; sort the evidence heads with `git show <head>:<test file> | grep '<old asserted value>'`, and a mutant receipt stays valid when the assertion it failed on is unchanged, web-embeds amendment 1; a receipt stamped `HEAD=<parent> dirty=N` held the next commit's change, so sort it by what its log shows, and when fix rounds added supporting tests instead of changing the cited tests, sort by a source line or the supporting test's name, since a grep on the cited test file is constant, site-reviews amendment; a cited test file identical across heads can still have a changed input: diff the fixtures and helpers it imports before carrying a receipt over, and where the amended sentence gains clauses only supporting tests assert, report the gap so a fixer extends the cited test under its unchanged name, panel-embed-code amendment; once a fixer has folded cases into a cited test that way, every older receipt of that name ran a weaker test: sort by the new variant list in the test file, and when a round restores code an earlier round removed, sort on the restored line itself, control-weight amendment), and says where the pre-amendment text lives (`git show <head>:<plan>`). An amendment that swaps an AC's input file (a refused capture for a clean one) also swaps every base input derived from it (main's paste and report), remade from the new file with the base commit's code, and names the file by its sha256 so the verifier and auditor of one head use the same one (site-slider amendment 11). A reviewer's suggested AC wording is set against the head's real output (the payload JSON) before it is adopted, not only the notes and counts: "one box labelled Button stays around it" was false for one real case, where unfoldable wrappers stay inside the labelled box (site-native-structure amendment 1). Before amending, it lists every expected last line each changed AC's test asserts (`grep -n 'want ' <suite>` inside the function) and reconciles them all in one amendment, because fix rounds change test expectations without anyone re-reading the AC text (review-loop amendment 1). No Amendments-list line starts with an AC id (`ac_start` accepts a leading `-`, a number or `**` before the id, so `- **AC7** (live) …` would join the AC list). Run `ac-check.sh`'s `ac_start`, `bad_id` and `live` regexes on the old and the new plan, and check the ids, the live set and the test-name lines are unchanged (review-loop amendment 2). An amendment that removes or defers an AC takes its id out of every line `ac_start` counts: a table row starting `| ACn` and a prose line that wraps to start with `ACn` keep it in `plan_acs`, so move it as "Was ACn: …" (header-bar amendment 1). The orchestrator then commits it, moves the old copy aside (`plan-approved-v<n>-….md`) and reinstalls it before the next reviewer or verifier (closing-cta, 2026-10-28), also when a fixer brief wrote the amendment into the in-repo plan: reinstall from `git show <head>:<plan>` as soon as that fixer returns (web-code-page amendments 3–4 were missed until review 5 saw the copy's AC4 contradict head). A verifier re-judging after an amendment diffs only the two copies' AC sections with wraps folded, carries over receipts for unchanged ACs, and re-runs the ac-check name grep (a rewrap can move a cited phrase) (site-motion, 2026-11-08).

**AC ids are `AC1`, `AC2`…** (never `AC2a`). **`(live)`** marks an AC only Justin can check (live publish → Sync, a native menu). The planner writes it right after the AC id at the start of the AC's line: `- AC3 (live): …`, also `- AC3 (proposed) (live): …` or `- AC3 (live, proposed): …`. A `(live)` later in the text doesn't count. The plan message lists every live AC before **go**. Agents can't tag ACs live.

2. **Not clean** → a fixer → a fresh review of that fix (`review-check.sh` until MOVE ON) → verifier.
3. **Clean** → dispatch the **AC AUDITOR**: a fresh Opus 5.5 xhigh agent (Justin, 2026-11-09), source read-only. Give it only the approved plan copy, the worktree, the head SHA, the base commit and its own folder `<evidence>/auditor/`. 4. **The orchestrator runs one command and reads its last line:**

   ```
   ~/.hermes/skills/autonomous-ai-agents/feature-dispatch/scripts/ac-check.sh --repo <worktree> \
     --base <base commit> --plan <evidence>/plan-approved.md --reviews <evidence> \
     <evidence>/verifier/ac.json <evidence>/auditor/ac.json
   ```

   `--reviews` runs `review-check.sh` on `<evidence>/review-<n>/`: a head with commits no clean review covers is NOT ACCEPTED.
   - `ALL ACCEPTED …` → the finish step.
   - `READY FOR THE USER …` → the finish step; the hand-over names the live ACs owed to Justin.
   - `NOT ACCEPTED …` → a fixer gets the `NOT ACCEPTED` lines plus both reports; then a fresh review of that fix → `review-check.sh` (until MOVE ON) → verifier → auditor → ac-check again. No round cap.
   - The same AC is NOT ACCEPTED for the same reason twice with no new fact → ask Justin, quoting the two lines.
   - Exit 2 (bad usage or an unreadable report) → fix the command, or send the file back to the agent that wrote it.
5. **After the finisher's rebase** (HEAD is no longer the head the reports proved, call it RH), when the rebase resolved no conflict, the finisher writes a **rebase receipt**: one log in `<evidence>/rebase/` (never inside `verifier/` or `auditor/`), first line `HEAD=<the new head>`, then the verbose output of every agent-run AC's test, last line `EXIT=0`:

   ```
   ( set -o pipefail; echo "HEAD=$(git -C <worktree> rev-parse HEAD)"; rc=0
     <AC1's test command> || rc=1
     <AC2's test command> || rc=1
     echo "EXIT=$rc" ) > <evidence>/rebase/receipt-<head7>.log 2>&1
   ```

   The commands are each `ac.json` row's `command` (for a report without it, the plan's test names and the logs' runs); `(live)` ACs have no line, and only the ACs' own tests run (a skipped test refuses the receipt). Then the orchestrator reruns step 4's command with `--rebase-receipt <evidence>/rebase/receipt-<head7>.log` before the two reports. Its `REBASE` line comes after the AC lines:
   - `REBASE  ACCEPTED: HEAD <head7> is a pure rebase of <RH7>, and the receipt ran on it`: HEAD has the same patches as RH in the same order (`patch-id --verbatim`, as `review-check.sh` decides it) and no merge, and the receipt ran on HEAD and ends `EXIT=0`. Each AC is then judged on the reports as before, for RH (their logs ran on RH, their base logs on the base RH grew from), and its test must also pass in the receipt.
   - `REBASE  NOT ACCEPTED: <why>`: a conflict resolved, a commit added, dropped or reordered, `main` merged in, or a receipt that ran elsewhere, didn't end `EXIT=0` or skipped a test. Every agent-run AC is then NOT ACCEPTED: take the full path (a fresh review of the resolution → verifier → auditor → ac-check).
   - `REBASE  NOT NEEDED`: the reports are already for HEAD; the usual checks apply.
6. **The orchestrator does nothing else here:** it doesn't open logs, rerun tests or judge ACs. That is the agents' and the script's work.
