# Things agents found (moved from SKILL.md)


Every `found_else` item an agent returns goes into `~/.hermes/plans/<project>/found-else.md`: a dated heading, then one line per item with its severity and evidence. That way the items survive a chat reset. Relay them to Justin with the plan or report. When he's picking his next work, offer the open ones, and strike each one once it's fixed.
- **Working through the open list in batches** (when Justin asks to clear the found items): group the open lines by area (layout/padding, text/line breaks, links/uploads, fonts, tests/tools) so one pipeline fixes several related items instead of one agent per bug.
  1. Write the batches to `~/.hermes/plans/<project>/found-batches.md`: per batch a kebab name, the item lines, a size estimate (scope only; models follow the role table), and which running or queued feature it clashes with (shared files from those plans' Touches/Overlaps sections). Mark items a running feature already covers and items that are site settings, not code. Test/tool items usually fold into a queued test-cleanup feature rather than a batch of their own.
  2. Send it in the plan format: questions first (fold tests in? start all planners now?), then one line per batch (size, model, item count, what it waits for), the build order, and the agent count per subscription.
  3. On go, dispatch every batch's planner at once, each in its own call, with one shared brief (`briefs/found-batches-planner.md`: read your section of found-batches.md, root cause per item with `systematic-debugging`, propose dropping or splitting an item that isn't real or is bigger than its batch, name files shared with each sibling batch and each running feature). Builds then follow the planners' `overlaps`, which often beat the guessed order (a batch the guess queued may share no file and can build at once).
  4. Items a plan moves between batches: update found-batches.md and steer the receiving planner if it's still running.
  4b. **Bulk authorization to assign and run found bugs:** reconcile the open, unstruck ledger against both live and queued ownership, using plans' Touches and `git diff --name-only` of live copies. Give every requested finding one disposition: existing owner, new isolated batch, decision-dependent, deferred, or non-code. Deduplicate repeated symptoms and partly fixed rows without closing the unfixed remainder. Group same-file issues into one pipeline, not one agent per finding. Keep the canonical ledger and `found-batches.md` current; if a separate assignment sheet is useful, link it from the canonical batch file so a reset cannot hide the new queue.
     - Write a compact ownership matrix before dispatch: exact finding, feature, source/test files, size, model/effort, prerequisites and reason held. Include tests, shared helpers and pending review work—not just production files. Identify findings by their exact wording and section heading or stable identifier; line numbers are supplementary snapshot locators because adding a ledger heading shifts every later line. Reconcile old symptoms against current merged fixes before assigning new implementation, and preserve any unfixed remainder. Planners may investigate read-only in parallel; builders touching the same helper must wait or receive a narrow written ownership boundary. Recheck actual diffs before each builder because plans can become stale.
     - Give parallel planners separate output ownership: each writes only its own plan and evidence, returning proposed reassignment/closure to the dispatcher. The dispatcher alone updates the shared ledger and ownership matrix during planning, so concurrent research cannot overwrite sibling assignments. Reuse a shared brief only after reading and merging its current contents; for a distinct batch round, prefer a round-scoped brief linked from the canonical batch file rather than overwriting an earlier round's recovery instructions.
     - Every batch follows the role table: every role a fresh Opus 5.5 high agent (2026-10-23). Explicit per-feature overrides still win.
     - Dispatch independent planners immediately under the user's bulk run authorization, recording its bounded scope in each brief. When Justin explicitly requests autonomous planning, review and merging for named batches, record that grant in the handoff and each plan; accept safe recommendations within that scope and advance planner → builder → separate fresh reviewer → test-first finisher → verified merge without routine approval prompts. Treat "loops" as this event-driven pipeline, not an infinite shell/cron loop or permission for self-review. New capability, changed prior policy, unapproved fallbacks and architectural trade-offs still return for approval; otherwise do not ask repeatedly to restart authorized work. Do not silently omit harder items or duplicate an existing owner.
     - Report new starts separately from existing work and held batches, with model and effort per line. Announcing assignments is not dispatching them; a planner is running research, not an implemented fix.
  5. **Later rounds** (new items agents found while the batches ran): place each one by the files it touches. An item in a queued batch's area goes into that batch's plan as an `## Addendum` ("write a short root cause + test for each before building; fix the small general ones, list the rest"), not into a new batch, since two batches in the same files can't build side by side. Make new batches only for areas no running or queued feature owns, and add a `# Round N` section to found-batches.md. A gap a reviewer reports in a feature it's reviewing (e.g. a case the approved answer didn't fix) goes to the batch that owns that area: steer its planner, and tell the finisher to record it as handed over instead of fixing it.
