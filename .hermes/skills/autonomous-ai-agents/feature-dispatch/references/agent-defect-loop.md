## The finisher holds the release

- **The finisher holds the release:** when the loop applies, tell the finisher to fix and commit, then stop with `status: ready-for-next-review` (the fix gets a fresh review; the verifier runs after MOVE ON). Figma: no merge and no BUILD bump yet. Leorna: no hand-over yet.
  - **Check integration before choosing a records-only finisher.** At reviewer completion, compare the current integration-branch tip and actual changed paths with the reviewed base (`git rev-parse main`, `git diff --name-only <reviewed-base> main`, adapted to the project). If a sibling changed shared source or semantic dependencies, put integration, refreshed same-base proof and accepted-decision records in **one finisher assignment**, rather than launching a documentation child and discovering the integration dependency afterward. Name any live release owner and coordinate through the established lock; never race its unfinished release. Pin the resulting base/tip and retain older proof as historical. After preparing the brief/admission artifacts, re-read the integration tip immediately before setting routing and dispatching, not only at initial intake. Give the verifier the expected integration pin and require an entry comparison before expensive gates: if relevant shared source or semantic dependencies already changed, return `integration-required` promptly rather than spending a full verification pass on a known superseded base. Classify committed records-only drift separately and preserve its owner; it is not permission to overwrite records. Every fix commit, records-only included, still gets a fresh review (`references/review-loop.md`).
  - **Close out records on that final candidate.** Synchronize the plan, ledger and handoff before `ready-for-next-review`; avoid an agent per stale sentence. For a records-only commit, verify the **complete** changed-path list is limited to the approved record files, as well as source/test equality; unchanged `src/` and `test/` alone cannot rule out changed tools, configuration or dependencies. Run applicable records checks, not another full application suite solely for documentation. Before handing off, recheck the integration tip: if it moved in shared code, steer the still-live finisher to reconcile it rather than knowingly launching the verifier on superseded inputs. Independent verification and required release/integration gates remain mandatory.

## Holds and accepted limits

- **Baseline-only validation holds:** separate source correctness from release acceptance. A committed candidate with an unresolved baseline gate may receive a fresh read-only review to classify the hold, but must not be relabelled `ready-for-review` or green. Once bounded diagnosis establishes that the remaining limits are pre-existing and no scoped repair is available, present one explicit choice: keep release held for separate remediation, or accept precisely named existing limits for this release. Do not commission repeated unchanged gate runs or widen the feature into tooling/font repairs without authorization.
- **Record each accepted limit before advancing the first unmet gate.** Distinguish a repaired defect, an explicitly accepted product limitation, a waived pre-existing proof gap and an owed live/installed-version check; acceptance is not a fix or a passing test. For a product limitation, record its exact trigger, user-visible consequence, supported subset and excluded mechanisms. For a baseline waiver, record the named check, release scope and prohibition on substitutes, narrowed expectations or weakened assertions. Update the plan, board and every subsequent role brief before resuming; separate decisions need separate explicit acceptance.
  - Resume the first unmet gate in the same turn: every fix commit, records-only included, gets a fresh review until `review-check.sh` prints MOVE ON (`references/review-loop.md`), then the independent loop verifier. Give both the original failed receipts and the current accepted contract. Require them to verify the supported cases and unchanged controls, not demand the superseded universal promise or restart mechanism research already settled by Justin. Keep accepted limitations and failed/unverified receipts honestly labelled; any failure outside their precise scope remains blocking, and neither acceptance transfers to another feature.

## Reopened findings

- **Verifier findings left, or any acceptance criterion not accepted:** a fresh FINISHER fix round, a fresh review of that fix until `review-check.sh` prints MOVE ON, then a new fresh VERIFIER. **Keep looping until every AC is accepted on one head (Justin, 2026-10-23; default for every story).** There is no round cap. Each reviewer and verifier returns `ac_status[{ac, accepted, test, screenshot, evidence}]`. Ask `❓ <name> [<project>] needs you:` only in two cases:
  - **A verifier or a review round that reopens a finding with new witnesses means the fix patched examples, not the class** (for a heuristic recognizer this is what trips the review referee's brake c; on 2026-10-29 Justin picked "Careful rules" both times it did). Brief the next finisher to fix the defect class conservatively (apply the new behaviour only where it is provably safe; everything uncertain keeps main's output), port the verifier's witnesses plus its own class-level controls, and keep the original positives green. Otherwise each verifier round finds one more witness and the loop never converges.
