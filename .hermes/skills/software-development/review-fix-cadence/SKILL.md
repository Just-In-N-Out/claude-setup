# Review → fix → review

## When to Use

Use for a multi-review coding workflow, a returned review with actionable blockers, or a user asking to fix before the next model reviews. This is not implementation approval or a reason to add reviewers a project does not require. Keep review/fix ordering canonical here; use `feature-dispatch` for native dispatch and model-provider mechanics, and the project skill for acceptance and publication permissions.

## Default cadence

For Leorna and every other repo (Justin, 2026-10-23: all-Opus default; 2026-10-28: loop until clean): **Opus plan → user go → Opus build → fresh Opus full review 1 → fresh Opus fixer → fresh Opus full review 2 → fresh Opus fixer → fresh Opus review of the fix commits → … until a review is clean (`review-check.sh`: MOVE ON) → fresh Opus verifier → blind auditor → `ac-check.sh --reviews`, looping fix → review → verifier until every acceptance criterion is accepted on one reviewed head → final hand-over.**

Use **Opus 5.5 xhigh** for build and fix passes, each a new fresh agent. Sol 6.1 is only a substitute Justin approves when Claude is at its limit; never switch silently. *(Superseded 2026-10-22 cadence: Sol build, Sol review first, Sol fixes.)* Reviewers are separate fresh agents, never the builder/fixer. A clean review skips a no-op repair. Preserve Opus planning, user-operated live acceptance, evidence collection and release permissions. In other multi-review workflows, repair actionable blockers before spending the next independent review on an already-known broken candidate.

## Loop until a review is clean (Justin, 2026-10-28)

Review → fix repeats until a fresh reviewer's review is clean: no P0, P1 or P2. Only then does the verifier run. *Why: in harness-guards, code from fix rounds 2–4 went unreviewed, and a fixer found two real bugs by luck. Justin: "help out a ton, but isn't going to be infinite."*
- **Severity** (this scale replaces `code-review-practice`'s P2/P3 meanings in Justin's pipeline):
  - **P0/P1:** a security hole, a guard bypass, a false AC, or a wrong block that breaks normal work.
  - **P2:** a bug a real person or agent could plausibly hit, realistic edge cases included (inputs, configs, git operations, macOS and WSL); anything that breaks an AC or the UI; a test that can't fail.
  - **P3:** cosmetic, docs, a hole only a deliberate evasion would hit, or a setup none of Justin's machines has. P3s go on the story's follow-up list (`<evidence>/follow-ups.md`), not to a fixer.
- **Scope:** rounds 1 and 2 review the whole story (Mini: round 1); from round 3, only the fix commits since the last review and what they touch. Anything else a delta reviewer notices is P3.
- **Brakes, so it always ends** (`feature-dispatch/scripts/review-check.sh` applies a, c and d):
  - (a) every P0–P2 names a concrete real-use scenario (5+ words: who does what, and what goes wrong); with none, it counts as P3;
  - (b) the scope rule above;
  - (c) a round with no fewer P0–P2 than the round before (when that round had any) → ASK JUSTIN;
  - (d) the same finding again (`repeats` an earlier P0–P2) with no new fact → ASK JUSTIN.
  - No fixed round cap.
- **Order:** verifier → blind auditor → `ac-check.sh --reviews` only after `review-check.sh` prints MOVE ON for the current head. Any fix after that (a verifier finding, a NOT ACCEPTED round, a rebase that resolved conflicts) gets a fresh review of that fix before the verifier runs again.
- Records, formats and what the main session does with each outcome: `feature-dispatch/references/review-loop.md`.

## Procedure

### Reconcile the latest authorization first

Treat an explicit instruction to apply an existing fix as implementation authority, not merely permission for another plan or diagnostic. Check it against the immediately preceding offer and standing project boundaries. If a material product choice remains unanswered, hold only its dependent work and ask that choice once with the actual user-visible tradeoff. Once resolved, combine the answer with the existing implementation approval and dispatch the scoped fixer without demanding another go. Record a changed work order separately from a waiver: applying a local candidate does not make failed checks pass, authorize a new validation method, bypass tool approval or permit publication.

1. **Freeze the input and preserve the report.** Record actual candidate heads, source state, complete findings, executed proof and outstanding acceptance holds. Passing ordinary tests do not cancel a reproduced adversarial failure. Keep old reports immutable and label their reviewed revision.
2. **Dispatch a scoped fresh Opus fix promptly when the earlier review has actionable findings.** Do not wait for the later reviewer solely because an old rule said both reports must arrive before any finisher. Load the project skill, `engineering-best-practices`, `receiving-code-review`, `test-driven-development`, `git-commit-rules` and applicable specialists. Verify each finding, fix valid introduced defects test-first, and return evidence-backed pushback on invalid/pre-existing claims. Brief the correction around the defect class, not only the reviewer's examples: carry the approved contract, an independent oracle, original hostile/resource controls and representative supported inputs. For parser, renderer or admission changes, include realistic ordinary/code-heavy content across supported sizes and nested/mixed grammar contexts; uniform padding and tiny shipped fixtures cannot establish semantic preservation. Treat an unapproved fallback or rejection on those valid inputs as a correctness regression, not an acceptable optimization. Surface already-known fallback or rejection choices before proposing another costly feasibility run; describe the real counting predicate and any ordinary-content false positives, because reusing an implementation constant is not approval of a new behavior. Reversing an accepted choice still needs the user's decision.
3. **Stop the intermediate fixer at the demonstrated boundary.** Re-run required gates and sensitivity controls, commit only scoped passing changes, and return each finding's disposition, exact new heads and real evidence. Return `ready-for-next-review` only when known blocking counterexamples within the approved contract are closed. A newly verified failing input class keeps the defect **OPEN**, even when the former witnesses and canonical suite pass: preserve the useful partial commit and exact failing probe/source binding, return `stopped` or partial, and do not send the known-broken candidate for approval. If further repair needs architecture outside the approved design, carry the partial source, witnesses and spent attempts into the project's read-only replanning route; apply the existing approval boundary to feasibility experiments too, rather than treating an earlier go as permission for broader implementation. No merge, publication, build/release metadata change or evidence posting in this intermediate pass.
4. **Send the corrected candidate to the next fresh reviewer.** Use a fresh Opus 5.5 xhigh reviewer. Rounds 1 and 2 review every affected repository's complete feature range (round 2 with focused scrutiny of the fix delta and earlier findings); from round 3, only the fix commits since the last review and what they touch, carrying every earlier `review.json` and the fixer's dispositions. Do not invent a second repository for a single-repo change. Never imply an earlier reviewer reviewed bytes written after its report. Use isolated snapshots and owned output/databases; restore mutations exactly.
5. **Use a fresh Opus fixer for each `REVIEW AGAIN` list** (the P0–P2 findings `review-check.sh` prints; P3s are follow-ups). Do not invent edits when Opus is clean. If source review is clean but required execution is incomplete, assign only validation and necessary records, not a speculative code fix. Carry prior attempts and elapsed time into a short discriminating check; require a new fact or changed condition before another costly run. Source/test/harness changes need their own authorized scope. Require the complete unchanged test population and lifecycle checks; focused passes, partial runs and author results do not substitute for a required independent gate. Stop validation-held if no authorized path remains. Every fix gets a fresh review; the fixer never approves itself. Run the separate Agent Defect Loop verifier when applicable, including its Required Validation Gates. A clean source review does not waive execution or that verifier.
6. **Preserve acceptance and permissions.** Never weaken scans, tests or failure semantics, or turn absent hosted/live proof into a pass. Capture real screenshots/logs during fixes, bind them to tested heads and privacy-check before authorized upload. Project rules still govern push, PR, merge, secrets/cloud changes and ClickUp posting.
7. **Handle quota and ownership explicitly.** Check actual usage before dispatch; ask before replacing a required Opus role. A projected reset is not availability. If Justin approved Sol as a substitute, Sol fixes may proceed while Opus waits. Do not stop another session's running reviewer to impose the order retroactively; reconcile frozen revisions and change the next safe transition. Treat nondefault shared routing as a conflict signal, not proof of a permanent reservation: establish its actual owner and unfinished dispatch interval from live or producing-session records before holding or changing it. Record the waiting role, owner and release condition; prefer existing completion events or the next task-capable turn over developing an ad hoc watcher. A monitor's expiry ends only the monitor, not the other owner's reservation. When fresh state clears the hold, recheck the prepared candidate and quota, dispatch the already-approved role through the established native rail in the same turn, verify its actual model and reset only this dispatch's overrides before bookkeeping. Do not ask for another go or leave an eligible reviewer idle behind the obsolete hold.
8. **Synchronize instructions.** Batch the plan, role brief, board and feature-owned handoff changes for each decision or phase transition, then steer the live owner. Replace the feature's current-status fields in place rather than appending contradictory current blocks; preserve prior outcomes in immutable evidence and clearly historical ledger entries. Supersede old wait-for-both-before-fixes holds and cancel obsolete reminders bound to the earlier phase/candidate. Keep report-only reviewers, fix ownership and final release authority distinct.

## Handle child-owned process notices

1. Match a completion notice to its owning agent, command and candidate before changing phase. A successful gate subprocess is not a completed fix pass or independent review; advance only from the role's complete returned report and verified handoff.
2. Keep an unexpected failed or interrupted gate with its current owner. If steering is needed, use `delegate_task(action="steer", subagent_id=<owner>, message=<concrete failure and required diagnosis>)`; require the full log, preserved receipt, supported cause classification and corrected gate proof if obtained. For a timeout or termination signal, establish who stopped the process and why before assigning a verdict: deliberately stopping a stalled startup/teardown run leaves execution incomplete, not a demonstrated product assertion failure. Do not infer the cause from a trimmed tail, start a duplicate fixer or run application debugging in the manager.
3. Batch routine subprocess notices into the owning agent's consolidated report when no decision or phase change is due; reconcile delayed notices by process ID and their already-recorded disposition. Do not reopen a diagnosed helper failure, restart a superseded helper or count an expected observer expiry as a product-test failure. Consolidate notices from the same helper chain when delivery permits. If a notification-only turn requires visible output, give one brief historical, scoped acknowledgment rather than an empty reply that triggers recovery; do not repeat the gate summary, ETA or an unverified claim that useful work is running. Do not infer a full test pass from a trimmed tail or wrapper exit. A successful retry is evidence for that attempt, not an explanation of the first failure; retain both until the owner supplies the diagnosis and source binding. Intentionally rejected mutation variants are not automatically product defects. Reserve the phase-change report for the verified complete role handoff.

## Parent intake before the next reviewer

- **Batch admission; do not turn it into another review phase.** Discover each report/manifest schema once and combine the required seal, source-pin, receipt and skill audits into one read-only pass. Reuse admitted observations where freshness rules permit, rechecking at actual input changes and ownership transfers rather than repeatedly loading unchanged evidence or workflows. Preserve every required admission check; the dispatcher does not run a duplicate application-validation campaign. Once admission succeeds, launch the prepared eligible reviewer before optional publication drafts, long-note cleanup or monitoring infrastructure work. Inspect captures before sharing them, but keep publication-only packaging and deferred operator acceptance separate from authorized code/local-gate review.

- **Re-anchor orchestration paths after a worker returns.** The shared terminal can retain the worker's isolated HOME/PATH even when HERMES_HOME still names the real profile. Check that environment before CLI/auth or board operations; use a verified absolute CLI and per-command operator HOME/HERMES_HOME plus an explicit DISPATCH_BOARD path. A null home-relative board lookup or missing CLI in that environment is not evidence the real task/account vanished. Read the authoritative target before any write; do not install tools, recreate a feature, reset user state or change models to repair this observation.

1. Read the complete structured report and its manifest/seal schema. Inspect whether payload entries are a list or a path-keyed mapping before iterating; do not interpret an absent guessed key as an empty archive. Resolve source pins against their declared base, candidate or input namespace rather than treating namespace labels as literal paths or comparing every pin to the candidate. Compare preserved working-tree files against the captured working-tree baseline, not raw Git blob bytes: declared checkout EOL conversion can legitimately make those representations differ without source drift. Preserve a reader refusal and verify the actual attributes and baseline pins; never normalize a protected file to satisfy the reader. Classify each check by its actual schema before dereferencing fields: command-execution records can reference receipts, while aggregate sensitivity, dependency or preservation records may reference structured evidence without a receipt or exit code. Resolve and validate report annotations, such as the record kind and receipt path, separately from the referenced raw execution payload. Compare all execution fields with the raw receipt; do not require equality between an annotated report record and an unannotated receipt, or drop unexplained differences to force a match. Classify authoring operations separately from read-only validation gates: verify the actual command, authorized write scope and intended delta before interpreting changed-source flags. A formatter or generator may legitimately change owned bytes, but its successful execution is not a passing test; subsequent qualifying gates must bind the resulting candidate bytes. Require execution status from real execution receipts; never default a missing exit to zero or count an aggregate record as another command. Preserve a reader failure and correct only the reader, without rewriting producer evidence or rerunning unchanged gates. Recheck claimed heads, full tracked/untracked state, scoped commit delta and identity before accepting transfer.
2. Recompute every declared payload's size/hash and compare the complete actual path set with the manifest plus explicitly excluded self-describing files. Reconcile declared totals programmatically, keeping execution receipts, aggregate checks, package-qualified test identities, reruns and mutant variants distinct. Keep parent intake records OUTSIDE the sealed producer directory, because even an extra harmless receipt breaks an exact-set seal.
3. Read real gate receipts and compare their recorded consumed-source hashes with the final candidate, not only their reported HEAD. Precommit gates may legitimately record an older HEAD while testing the eventual committed bytes; document that byte-identity binding instead of rewriting old receipts or pretending the commit existed earlier. Reuse matching execution evidence; changed consumed bytes require fresh affected checks. Keep candidate defects, harness/environment failures and admission violations distinct. Credit a corrected gate only from genuine required execution on the matching candidate; a successful wrapper or later quiet resource sample does not repair an earlier failed invocation.
4. Verify required skill loads against successful tool results, not the worker's checklist. Audit conditional requirements against events too: an unexpected failure can activate a debugging-skill requirement after kickoff. Disclose an omitted load separately from source findings, preserve valid scoped evidence, and route any outstanding required diagnosis to its owner; do not invent historical compliance or replay unchanged successful gates merely to fill a checklist. Inspect current-candidate screenshots yourself before sharing, preserve local-versus-hosted labels and capture caveats, and distinguish a clean publication subset from a differently scoped full-directory scan.
5. Treat intake as artifact admission, not independent application verification. Read sealed evidence without rerunning report/finalizer writers. Prepare the next fresh review against the corrected immutable full ranges plus the focused fix delta, carrying prior findings, the original failure/diagnosis and every remaining acceptance hold. Use `concurrent-state-validation` for deeper seal, source-freshness and ownership checks.

## Validation and reporting

- Returned actionable blockers advance to a fresh Opus fixer before the next unstarted full review.
- No verifier starts before `review-check.sh` prints MOVE ON for the current head.
- The next reviewer receives the corrected immutable heads and earlier proof.
- Clean reviews do not force unnecessary edits.
- Final behavioural fixes retain independent checks and all live/hosted/privacy holds.
- Forecast and report the fix pass end to end, including dispatch preparation, tool setup, worker execution and parent evidence intake. Label a worker-only range separately; do not hide coordination time behind a short test or child duration. Batch the required intake and avoid repeated unchanged bookkeeping checks, while retaining source-freshness checks at actual ownership transfers.
- Report the feature, model/effort, corrected revision and next gate in one phase-change line.
- When the user asks whether anything is working, check the named feature's live worker and board, then answer yes or no first with its actual role. A prepared brief, queued reviewer, completed test run, routing watcher or another story's worker is not active work on this feature. If an already-approved next role has become eligible, start and verify it in the same turn before reporting it running. State a failed helper's scope without substituting repeated reassurance for a truthful activity answer.
- When the user asks whether the story is done, answer yes or no first, then name the current blocker and remaining stages in plain words. Distinguish a working prototype from an applied application fix, local checks from independent review, and reviewed code from operator acceptance or shipment. Do not make a slice estimate sound like a story-completion estimate.

Read `references/scenario-checks.md` when validating the cadence or choosing an ambiguous next phase. Structural checks and scenario expectations do not prove an unexecuted model pipeline.
