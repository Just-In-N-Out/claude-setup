# Rendering validation for picture and hover changes

## Establish the actual cause
1. Inspect the supplied screenshot and identify the visible seam, frame, clipping or motion in plain words. Separate an unwanted effect from a rendering defect in an effect the user wants to keep.
2. Read the live page and its styles without changing the site. Inspect image alpha, wrapper paint, stroke, shadow and pseudo-elements; compare the matching Figma layer or explicitly label a sister design as indirect evidence. Readers, hidden boxes, overflow and the page's own CSS: `references/live-site-reading.md`.
3. Render the real media at the paste's actual widths. Corpus grey stand-ins cannot establish transparent-image fidelity. Preserve their reports, then run a separately labelled real-media comparison rather than dismissing a score change as noise. The renderer's `settleCapture` never resolves on a page with scroll-driven animations (`animation-timeline: view()`; 30.12's pinned menu bar is one: `snap` stops silently after 991 with no output for wider widths, djtrees planners 2026-11-02): render such a page with reduced motion and a bounded settle; geometry-only probes can wait for `document.fonts.ready` plus ~1.5s instead (checked equal at 390 on DJ Trees). On a very tall page (16.7k px) `chrome.ts` `screenshot({clip})` (`captureBeyondViewport`) can hang past 120s: scroll the region into view and take a plain viewport shot (djtrees-stack-gaps). Any single `page.screenshot` can also hang with no end while another Chrome-heavy run (a whole-suite mutation pass) shares the CPU: race each capture against a ~20s timer (clear it after it settles, or a leaked timer logs false time-outs), retry once, and render screenshot sheets after heavy runs finish (djtrees-cta-center reviewer). It also writes a slide's own settings as `#brxe-<id>`, which Splide renames (Bricks writes `[data-id="brxe-<id>"].splide__slide`), so a hand-built slide with its own settings loses its photo and height in replay/snap: emulate Bricks' selector before judging it (B-Dry v3, 2026-10-29). A rule added inside `style/picture.ts` `picture()` that also feeds `states.ts`/`motion.ts` (they run for every node) must leave out what `picture()` leaves out: a layer named or linked as a video returns `videoStyled` first, so a helper keyed only on the node's fills applies the still's look to the Video's hover and Motion; probe a `Video: https://…` still with a Motion track and a hover variant (djtrees-faint-picture review). Before scoping a picture-look defect, sort the pictures by asset key: `fill:<hash>` is the original upload (nothing of Figma's paint is in it, so style must write fill opacity, stroke, blur), `node:<id>` is Figma's render with them drawn in; a styleAll probe of asset keys plus the live PNG's strongest alpha shows which are really wrong (djtrees-faint-picture: one of four "black" trees was).
4. Before reporting "not reproduced", sweep the whole laptop band (1440/1366/1300/1280/1269/1200/1100/1024/992) at DPR 1, 1.5 and 2, not only wide desktop, and compare every symptom in your own other-findings list with the reported one: a defect you logged as "separate" at a neighbouring width is often the user's. Do not infer CSS viewport width or DPR from a screenshot's physical width alone: zoom/rescaling/noninteger DPR can produce the same dimensions. Compare subject and frame pixel geometry with known-width captures before attributing the screenshot to a laptop crop. At fractional bounds, sample adjacent-pixel derivatives across a small band around floor/ceil boundaries rather than one rounded column; retain the first reader as diagnostic when it misses a visually confirmed cut.
5. On a textured backdrop, pair the unchanged page with a capture hiding only the picture, then subtract that backdrop before sampling the picture-edge discontinuity; truck/photo detail and a smooth shadow crossing the bounds are not themselves a seam. Preserve original captures and one-property interventions. A deliberately restored old box shadow qualifies the reader, not the user's newly reported state: if fresh output is already clean and disabling `will-change` changes no meaningful pixels, keep the diagnosis held rather than calling the hint or stale cache the cause. Inspect cropped source pixels separately from compositing; a fixed-height `object-fit: cover` picture can expose a different straight-edge failure on laptops.

## Alpha-only eligibility before sizing
- Before implementing a transparent-cut-out-only layout rule, trace where real pixel alpha becomes available relative to conversion. A snapshot image hash/dimensions, IMAGE paint opacity, rendered-export key, absence of solid fills or alpha-capable extension does not establish source transparency. If bytes arrive only after `convert`, stop at the approved boundary for an explicit metadata/extraction propagation scope; do not infer alpha from names/structure or rewrite emitted styles in the panel.
- Prove the boundary with identical pre-conversion structure and independently verified transparent/opaque pixel substitutions. A browser fixture that inserts a transparent URL through `fillAssets` after conversion proves rendering, not production cut-out eligibility. Preserve its original geometry/seam oracle separately if a narrower decision invalidates that fixture's admission.
- When planning alpha metadata, bind evidence to the exact selected fill/render source and same-run export bytes; a node id alone is not rendered-content identity. Require original-source evidence as well as final-render evidence for image-backed renders, because an opaque rounded photo can acquire transparent corners or shadow padding during export. Keep missing/ambiguous/corner-only evidence on the existing output and list the conservative coverage trade-off before approval.
- Finish extraction metadata before the first normalise/style/convert, using a bounded raw-source inventory if necessary; do not propose convert→inspect→convert or an emitted-CSS patch to learn the final asset list. Compare optional-metadata legacy snapshots byte-for-byte, and coordinate plugin/main.ts, shared/messages.ts and ui/main.ts with active panel/diagnostic owners before promising an isolated one-file layout fix.

## Shadow mappings and adversarial controls
- Map box-shadow/Figma blur radius to half that value for CSS filter drop-shadow's standard deviation; verify the source semantics rather than trusting a plan or a test that pins the old assumption. Layer blur has its own mapping and must not be halved twice.
- Compare an opaque photograph with rounded corners against the old box shadow, sampling pixels outside the image and at the corners. In `test/fixtures/builders.ts`, `image()` takes `radius`, not `cornerRadius` (the latter is overwritten); assert the computed radius before trusting a rounded-photo regression. Distinguish the clear corner/shadow region from the narrow CSS antialias band and record whole-image differences separately rather than claiming exact pixel identity. Add a transparent-cutout case that measures the luminance step just inside/outside the former rectangle. Require both to pass; removing the edge step alone misses excessive blur.
- Test multiple shadows with orthogonal, zero-blur offsets. Sequential filter functions can create a third shadow at the sum of the offsets because each consumes the previous filtered output. A warning about darkness is not an adequate description of this shape change.
- If independent-source shadows need a new rendering mechanism, stop for a revised plan or explicit fallback choice. Do not silently remove shadows, retain an incorrect chain, or claim a fallback preserves Figma. Keep a single-shadow correction separate so it can proceed while the broader decision waits.
- For an SVG filter carried in a CSS data URI, compare a host-palette-variable control with same-document inline definitions before choosing the transport: the separate resource may use its fallback instead of the host colour. Obtain approval before snapshotting palette colours. A local img/background probe establishes only that browser's transport feasibility; require the exact installed-Bricks paste/save/copy-back, compiled CSS, CSP and intended-browser proof, plus responsive filter-region bounds, before calling the mechanism supported. Never loosen upload or code-execution policy to make the probe pass silently.
- Distinguish a real Figma stroke from a shadow seam; removing an intentionally drawn border is a separate user choice. Keep source-image fringes separate from converter defects until real-alpha/lossless comparisons establish the cause.
- Exercise each required browser with intended-shadow positive controls, not only a white phantom location or an accepted computed filter. A missing filter can leave the source visible and the phantom white while drawing neither intended shadow, creating a false pass. For resource-transport failures, compare encoded and base64 data URIs, same-origin external resources and same-document definitions; retry a settled top-level page before assigning the failure. Record browser versions and measurements in task evidence rather than treating one failed transport as a permanent browser limitation.
- Test a single CSS `filter: drop-shadow()` in WebKit on image content, not only Chrome: Safari 26.5 (WebDriver snapshot) and iOS 18.6 Simulator framebuffer clip it to the element's box on an `img` or background-image box (a solid-colour box draws it). Adding `will-change: filter` fixes macOS Safari but stays intermittent on the iOS Simulator (the shadow outside the box vanished in roughly half the repeated captures, still gone after 15 s), and `translateZ(0)` is worse and overrides picture transforms. Judge iOS from many repeated captures per page, never one: a single good frame hides the loss. A cut-out whose shadow stays inside its box passes and hides the failure: include an opaque photo and a shadow reaching past the box edge.
- Before shipping `will-change` (or any compositing hint) on every matching picture, measure its layer and memory cost with Chrome CDP `LayerTree` on a real page and on a generic grid of many matching pictures at desktop and phone widths: each hinted picture, and overlapping later content, gets its own layer, and backing store scales with DPR (about 9x at an iPhone's DPR 3). Record the measured cost as a trade-off the user accepts; a unit test of the emitted string is the only CI guard, since Chrome draws the shadow without the hint. For real on-screen WebKit pixels use `xcrun simctl boot` + `openurl` (loopback) + `simctl io <udid> screenshot`, then shut the simulator down; `screencapture` lacks permission here and only raises a macOS prompt.
- A filter makes a picture a stacking context: its shadow then paints over later non-positioned siblings (a caption under a photo) that a box shadow left on top. Measure glyph pixels of later text inside the shadow's reach against the old output.
- Reject bounds pixel-equality results when the reference transport itself did not render shadows. Derive and state minimum/maximum picture sizes for any normalized/fixed-region experiment; record logical surface estimates separately from actual allocations, and never present navigation/wait/screenshot wall time as GPU/frame cost. Preserve failed or invalid raw measurements rather than silently repairing them.

## Autonomous compatibility investigation
1. Record approvals separately: visual goal, transport, fixed-versus-live palette colours, and permitted side effects. Preserve the chosen colour policy even if an alternative transport happens to support more dynamic behaviour.
2. Probe locally using actual browser rendering, bounded sizes and positive/negative controls; inspect legitimate local exports/source and the public site's compiled CSS/CSP without modifying it. A schema or GET response cannot prove save-time sanitization or installed-version paste/copy-back.
3. Label each conclusion as measured, inferred or unproved for browser rendering, transport retention, CSP, palette inheritance, bounds and cost. Do not use screenshot/navigation duration as a rendering-cost measurement.
4. If a required browser fails, stop that route. Propose a separately scoped alternative with its exact output files, security/signature requirements and proof gates; do not silently switch carriers or introduce structural Code output. Keep existing independently verified corrections on their branch while the larger route waits.
5. Bound the investigation. If installed acceptance cannot be established with available read-only/local evidence, return the exact remaining proof obligation and smallest user action instead of repeating speculative probes or claiming local HTML is installed Bricks.

## Responsive card and spacing validation
1. Before broadening card recognition or releasing a card's height, trace whether each picture remains in flow or becomes an absolute cover/background. Test fixtures on both sides of the cover classifier's threshold, including a tight caption, an overlaid caption, a GROUP, an image-filled frame and nested pictures. In Chrome, assert photo height and shape as well as width and containment: an absolute photo can remain inside a collapsed caption-height card and pass containment-only checks. Test aspect-ratio floors with a paragraph that fits at design width but needs more phone height, on fixed and hugging widths, clipped and plain; assert both dimensions. `max-width` can transfer a height ceiling through the ratio, while `fit-content` can widen a hugging box as its content grows.
2. Before changing a tablet margin or gap formula, audit its effective value at every narrower tier, including tiers with no explicit emitted override. Add a generic row that stays on one line on tablets but wraps or goes two-per-row on landscape phones; compare both emitted settings and actual geometry against the exact base. A tablet declaration can silently carry into a narrower layout where the formula's assumptions no longer hold. Demonstrate phone-only branches through conversion and Chrome, not only mocked layout facts.
3. When fractional padding changes corpus scores, preserve the reports and compare matched exact-base/candidate renders with equal font and motion policy. Inspect every affected side, chip and downstream row: subpixel vertical changes can cross raster snapping boundaries without changing wrap or lint counts. Repeat unchanged captures to distinguish variation from a deterministic regression; identify changed pixels and geometry before proposing a precision correction. Unchanged section crops or a plausible rasterization explanation do not waive the no-worse gate. Keep installed-Bricks decimal-setting retention separate from renderer proof.

- The layout lint's only overlap check (`text-overlap`) compares text with text: a placed picture or drawing over words, questions or controls passes snap and corpus green. Probe art over words yourself: intersect each placed element's box, clipped to its section, with every visible text box at each width (DJ Trees FAQ tree covered 2–4 texts at 320–991 with the lint clean; djtrees-faq-art).

## Hover and clipping proof
- Test a phone tap over CDP with `Emulation.setDeviceMetricsOverride({mobile:true})` + `Emulation.setTouchEmulationEnabled` + `Input.dispatchTouchEvent` (touchStart, then touchEnd with `[]`): Chrome then fires the real sequence (mousemove/:hover, mousedown, focus, click). Headless `Input.synthesizeTapGesture` fires only touchstart/touchend, so a test built on it proves nothing; prove the helper with a control tap on a plain link. Once a CDP mouse move has happened in a page, Chrome moves `:hover` back under the mouse after every tap: run tap checks in a fresh page with touch on before any mouse event. Chrome never hit-tests a face turned away with `backface-visibility: hidden`: to prove such a face can't take a tap's click (WebKit may hit-test it), inject `.face { transform: none !important }` and tap with reduced motion. Chrome fires the tap's click ~1ms after touchend, so an instant pointer-events switch lets it land; `pointer-events 0s linear 50ms` with `transition-behavior: allow-discrete` stops it. A mid-turn sideways-overflow check needs a card tall enough to leave the gutter (perspective growth scales with height). To animate a custom property from Bricks custom CSS, register it with `@property` and write its syntax escaped (`"\3C number\3E"`), so no raw `<` meets a sanitiser; Chrome registers it the same. Backslashes in element settings and quoted `url("…")` in element custom CSS survive Bricks' save on Justin's site (2026-10-27): check the live `post-<id>.min.css` before calling an escape a live-only risk. A data-URL SVG background stretched with `preserveAspectRatio="none"` keeps its stroke weight only with `vector-effect="non-scaling-stroke"`. Bricks writes an element's own settings under `#brxe-<id>`, so a class rule (even with `:has()`/`:is()` states) never overrides that element's own `_overflow`, `_opacity` or transition: a state that changes one (unclipping while a child shows) goes in the element's own custom CSS (`#brxe-<id>:has(…)`, as `behaviours.ts` does for hover layers), and a class's show/hide uses a property the element never sets (`visibility`). Test a popup's hide-grace with Instant (0s) timing too: a fade's own visibility delay masks a mutant that drops the grace. A grace on `visibility` alone doesn't keep a fading element painted (opacity drops at once with Instant timing or reduced motion): sample computed opacity during the crossing, and combine hide-grace with a card hanging outside a clipping photo: check ancestor overflow/stacking and outside-frame hit tests during the gap. A child remaining visible at opacity 1 does not prove its ancestor stays unclipped through the grace. Unclipping a box on a state (`:has(…) { overflow: visible }`) shows everything it crops: its picture's square corners and any layer drawn bigger than the box (a crop). Check `elementFromPoint` 2px inside a corner and just outside the box, at rest and with the state on. Anything drawn past a text's own box (a pseudo-element ring) must also be probed with the text flush against the gutter (right-aligned, or ending a full line), including transforms, larger nested runs and permitted wrapping: `1lh` need not equal the inline-block’s used height. A ~24px overhang in a 16px phone gutter scrolls the page sideways while centred fixtures stay green. Load transformed and no-transform controls in separate fresh documents; in Chrome 156, removing a pseudo-element's rotation live left stale `scrollWidth`, while the identical override applied before layout gave the true control. Before narrowing a rule to layers drawn past their box, measure at 390 and 320: px-sized children on a box that keeps its shape and shrinks hang out on phones even when drawn inside. Browser tests find a paired sibling (a trigger's card) by its content, never by DOM adjacency, or a mutant that swaps their order passes. In `test/browser/render.ts` the call-to-action and card fade-ins start only when the element enters the viewport (`render-motion.ts`'s IntersectionObserver), so clips below the fold come out blank however long you wait: for pictures only, after measuring, inject `.brx-animated,[data-animation]{animation:none!important;opacity:1!important}` (djtrees-cta-center). To prove an injected font loaded, list `document.fonts`' `FontFace` entries with their status: `document.fonts.check()` stays false while a family's unused Google subsets remain registered and unloaded (djtrees-top-align verifier). A heading filled with a picture is drawn under the replay's grey stand-in, so a shot shows the stand-in, not the words: for a visual receipt of its fit, measure first, then on the page only set its `-webkit-text-fill-color` dark, a light background and `position: relative` with a high z-index, outline its column, and clip wider than the viewport (djtrees-phone-headline auditor). A change that pads, widens or offsets a sideways strip's box must be probed with a strip drawn without auto layout: the cards past the frame's edge stay absolute at `left: Xpx` from the padding box, so padding moves the flowing cards but not the placed ones (djtrees-strip-edge review). To check a `100vw` layout under a Windows classic scrollbar, run Chrome through a `CHROME_PATH` wrapper that drops `--hide-scrollbars` (the repo's `launchChrome` passes it): headless Linux Chrome then shows real 15px scrollbars. A strip with controls or card arrows holds its Code element as its last child (`display: none`): read cards by `.strip-card` or non-zero width, never `strip.children` (strip-edge builder: a zero-size "last card"). Fixture layers named like a Figma kind ("Line") get no `data-label`, so `[data-label="Line"]` matches nothing even where they show: assert a counted selector matches at the design width before asserting it vanishes. Comparing base and head renders box by box, timed transforms (a carousel's lifted current card) make `getBoundingClientRect` differ between two loads: compare offsets plus borders/paddings, and run base against base first (djtrees-stack-lines). A test that re-adds Bricks' `.brxe-block{align-items:flex-start}` proves a written stretch only for Blocks (`.brxe-div` has no default): when a fix changes the element a fixture emits, re-run the mutants whose kill relied on Block-only CSS. `elementFromPoint` uses half-open boxes ([0, 24) misses x=24, [366, 390) holds x=366), so a symmetric "N px in from each end" probe can pass on one side and fail on the other: leave clear space rather than sizing a control exactly to an edge.
- Qualify wrapper matching as one-to-one ownership: two newly inserted wrappers with same-named, same-kind, same-size descendants must not both consume one unmatched own layer. Include distinct replacement/new words, reverse sibling order, exercise the missing-main fallback and ties among original layers; first-wins reservation alone can still shrink the added content. Reject unproved ownership rather than inferring identity from traversal order, while positive controls retain single and multiple independent replacements. Inspect emitted margins and parent minimum separately; a passing single-wrapper fixture can hide shrinking newly added content. Preserve existing row.reflow phone stack margin resets when checking a positive wrapper: its drawn border box, responsive minimum and parent's counted footprint are different quantities.
- A rendered SVG background has no DOM `path` nodes. For source-backed paint-offset measurements, decode the actual computed data URL and validate intrinsic size, viewBox, `background-size` and positioning before applying its path coordinates. For a fixed-stroke background centred at source (0,0), use an explicit user-coordinate scale origin; percentage origin/padding can shift and clip paint while box checks pass. Qualify whole/static and reduced-motion pixels as well as animation; preserve a failed DOM-path probe as invalid instrumentation, not a product failure. Keep this computed-geometry proof separate from screenshot pixels.
- Capture original idle, original hovered, corrected idle and corrected hovered states at each affected width, using identical scroll position and crop. Compare label/title/icon rectangles relative to their card, not raw document coordinates; a scrolled screenshot can look like displacement even when the card's internal geometry is unchanged. Label provisional and final candidates with their tested revision, and preserve the strict motion oracle while fixing the cause. When a section extends above the viewport, do not feed its negative viewport y into a clamping bitmap crop: it captures a different part of the page. Use `page.screenshot({clip})` with explicit document coordinates, pin the same section box and scroll for both revisions, and retain the first viewport crops as diagnostics.
- Inspect both painted bounds and the parent's minimum/content/reading-room accounting when a hover variant adds a transform wrapper. CSS compensation can restore the arrow's visible position while planning still reserves the full wrapper size and changes responsive padding or wrapping. Use a tight-width browser fixture to prove both representations agree, with a deliberate hover-resize control so stabilization cannot erase designed motion. Containment alone does not prove motion preservation.
- A fix that moves a box's inner space out of it (a min height or inner padding into the parent's padding) must be measured at the design width on a painted, an outlined and a bottom-pinned-placed-layer variant: the space leaves the paint and pinned layers ride onto the words while the user's pastes and lint stay identical (faq-answer-space review F1/F2). "Draws something of its own" is `fills.length`, `stroke`, `effects.shadows`, `effects.backgroundBlur` (the fields `looks.ts` `unpainted` clears), not `label-box.ts` `painted`/`outlined` (they skip image and <10% fills and need a stroke on every side). In a no-auto-layout fixture a box-sized rectangle behind the words folds into the box's fills; a layer reaching past the edge stays placed.
- Distinguish a title staying on one text line from it sharing the label's flow row. Assert both rectangles against the literal acceptance wording and inspect the saved before/provisional pictures: equal title heights can conceal an already-stacked base card. If matching the own card is proven but the requested same-row outcome would need an unapproved base-layout policy change, preserve the working fix and report that scope discrepancy rather than silently treating the two outcomes as equivalent.
- Test no-glare changes independently from the retained zoom and load animation. Restrict tests to the behavior forbidden by the user's choice, allowing legitimate static tints/overlays.
- A "nothing changes up to width W" AC proven by rect comparison (or a head-minus-feature twin) can't see a clip or paint swap: replacing `overflow: hidden` with `clip-path: inset()` keeps every rect but drops border-radius clipping, and an inclusive `@media (min-width: W)` applies it at W itself; probe such swaps with a rounded variant (inner corners only too) using pixel samples at W and above (djtrees-panel-edge review).
- Prove clipping with pixel samples or elementFromPoint outside the frame during the transform; the parent's getBoundingClientRect does not change when a child scales, so comparing that rectangle cannot prove clipping.
- Measure hover state and scale through the transition (a live site's hover end state: `references/live-site-reading.md`). Record a GPU-dependent soft-to-sharp change separately from a bright flash; do not remove an approved zoom or add will-change as an untested fix.
- Timestamp animation captures and report achieved cadence and sampling gaps, not just the requested frame rate. A burst scheduled at 30 FPS can capture fewer frames under load; stable sampled rectangles establish geometry at those samples, not uniform 30 FPS smoothness. Preserve the original burst and distinguish geometry/motion acceptance from any still-unproved cadence claim.
- Report browser coverage exactly. Compatibility documentation and headless Chrome tests do not prove an installed Bricks round trip or an exercised Safari result.

## Same-document definitions planning
- Keep a resource ID and every reference in the same carrier's settings when evaluating paste-time self-ID rewriting; the existing 2.4.1 rewrite fixture does not prove 2.3.9 behavior. A local wrapper/adjacency simulation is not a save/sanitization/signature proof, and adding Code/IR/emitter transport requires its own approval.
- Include multiple document positions and duplicate/revised carriers in inline SVG probes. A Safari26.5 scratch zero-size carrier with a fixed user-space region rendered the first HTML picture but removed a second lower picture; changing only to object-bounding coordinates restored that fixture's source/shadows. Do not infer a general responsive region or global minimum size from this control.
- Preserve failed literal-RGB colour assertions and add same-browser colour/alpha controls before declaring them colour-management noise. A white phantom plus missing intended shadows is never success; neither a plausible ICC explanation nor a widened tolerance closes the gate.
- When an oracle measures the target site, record where the words are drawn (their ink or text range rects), not only the element's box: a 497px h2 box at x 233 hid centred words (ink 372-589), the plan called it left-aligned and a box-based AC passed (header-bar F5). Also check that the reference page's own fonts load in the capture (`document.fonts.check` per family and weight; bdryswi.com's Roboto 600 doesn't, so its line counts are fallback metrics; fetch the site's CSS and request each face URL: when the exact weight's face fails, Chrome falls back to the next family in the stack, not to that family's loaded neighbour weights), and that existing content another AC freezes already matches the reference at every AC width (after-faq-sections AC7).
