# Reading a live website (website importer, compare tool, live probes)

Read-only GETs of public pages, through the repo's Chrome driver (`test/browser/chrome.ts`). Never log in, never write.

## Access
- **A range read from a page without its styles** (staging-fit planner, B-Dry 2026-11-09): count each range's declarations that become null against its wider neighbour (`web.code.nodes[*].decls[range]`); a styleless range drops most (922-991: 18,895) and the next narrower one adds them back (601-767: 20,211), and its boxes, shown counts and the paste all follow while `site:check` agrees with the bad capture. Sites serving CSS as deferred bundles (Jetpack `_jb_static`, `media="not all"` swaps) can do this under side-by-side reads. Chrome 156 makes an empty sheet (`link.sheet` non-null, 0 rules) for a stylesheet answered 503, so "applied" needs the link's error event (a capture-phase listener in a start script) or `responseStatus` < 400; another site's failed sheet reports status 0, so only the error event shows it (staging-fit-capture builder).
- **Where a capture's minutes go** (capture-speed planner, B-Dry): read the file's own `web.timings` (authored values aren't timed); to tag every DevTools command by tab and phase, wrap `browser.conn.send` at runtime (evidence/capture-speed/planner/profile.mjs). 93% of a capture is `CSS.getMatchedStylesForNode` (~84 ms, ~626 KB, 92% of it `inherited`). Its `inherited` entries hold each ancestor's matched rules and inline style byte-identical to that ancestor's own answer, except across a shadow tree (a `<details>` adds a slot: `inherited.length` = parent count + 1); `attributesStyle` and pseudo-elements are never in it. Attributes that give an element an `attributesStyle` in Chrome 156: `lang` (`-webkit-locale`), `dir`, `hidden`, `draggable`, `contenteditable`; `data-*`, `aria-*`, `role`, `title`, `href`, `src` don't (capture-speed builder). A document answered with `Fetch.fulfillRequest` has IP address space Unknown, so Chrome 156's Local Network Access refuses its requests to other loopback/local origins (`setPermission local-network-access` doesn't help; same-origin loads): replay only pages that came from public addresses (capture-speed builder). Asking leaves and deriving ancestors cut 2,037 asks a range to ~578.

## Writing readers
- The capture enables the Network domain with zero buffers (`src/web/lost.ts`), so a tab's document body is heard only through Fetch at the Response stage (`replay.ts` `recordTo`; the served page now comes from the tab's own answer, `src/web/served.ts`). A kept local page (`F2B_REPLAY=local`) can't load another local origin's script, so a widget fixture draws nothing there: test "answered from the kept page" at the session. Before changing which requests a capture makes, grep the tests that count page requests (`capture-replay`, `human-check` AC3) (site-reviews fixer 1).
- **Holding a Chrome to read-only:** CDP Fetch enabled on a page's session doesn't pause a cross-site frame's requests; enable it on the browser target (no session; `Browser.on` in `chrome.ts`) to pause every tab's, frame's and worker's created after `Fetch.enable`; a page already loaded keeps posting, so hold it with a second flattened session on its tab (`Target.attachToTarget` again; its own Fetch works beside the first session's), and `failRequest` with `Aborted` keeps the page on its document (site-menu fixer 2). Fetch on a page's session doesn't see what the page's service worker answers (`respondWith(fetch)`, page loads included): a guard held on page sessions also sets `Network.setBypassServiceWorker({ bypass: true })` for its span (it only works after `Network.enable` on that same session), and its test fixture registers a worker (site-menu review 3). `Target.setAutoAttach({ autoAttach: true, waitForDebuggerOnStart: false, flatten: true })` on a second session of the tab attaches what already runs beside the page (another site's frame, the service worker, a dedicated worker); a Fetch per child holds the frame's and the service worker's requests, but a dedicated worker's session has no Fetch, so one already running stays outside such a guard (fixer 3); it reaches only direct out-of-process frames, so recurse for nested ones. To hold the windows a page opens before their first request, browser-level `Target.setAutoAttach({ autoAttach: true, waitForDebuggerOnStart: true, flatten: true, filter: [{ type: "page" }] })`: act only on `attachedToTarget` with `waitingForDebugger: true` (pages already there and your own sessions arrive with `false`), and on a window whose `openerId` is the pressing page (no-opener `target=_blank` windows still carry it) send `Network.enable` + `Network.setBypassServiceWorker` + `Runtime.runIfWaitingForDebugger` at once, never awaited one by one (a no-opener window doesn't answer until let go); `autoAttach: false` detaches every auto-attached session (fixer 4). Fetch never sees WebSockets: launch with `--proxy-server=http=direct://;https=direct://;socks=socks5://127.0.0.1:<a refusing SOCKS end>` plus `--proxy-bypass-list=<-loopback>` so only non-http(s) traffic hits the dead end. A `<link rel=preconnect>` is the one connection no request guard sees (a good test of resolver rules) (`tools/lib/read-only.ts`, staging-fit-renderer fixer 1). The guard holds only while the client is connected: closing a tab and then the browser at once lets the page's `pagehide`/`visibilitychange` `sendBeacon` and keepalive POSTs out (6 arrived; 0 after the tab went to `about:blank` or 3 s passed before the close), so probe with a page that beacons as it hides and goes, and count what the server got after the tool exited, on the OK path and every stop path (review 2). End a guarded Chrome by SIGKILL of its process group (launched detached, so a wrapper script goes too) while the client is still connected, never `Browser.close`, which releases requests Chrome still holds (6 of 6 arrived; 0 when killed): first close every page, frame and shared or service worker target with the guard answering and wait ~300 ms of quiet (closing requests are paused 2–4 ms after the tab is gone). A tool dying without its `finally` (SIGTERM, EPIPE from `| head`) orphans Chrome unguarded and the page keeps POSTing: add signal handlers (SIGQUIT too: a Chrome in its own group no longer dies with Ctrl+\) and a synchronous kill on process `exit`; SIGKILL of the tool itself stays open (fixer 2, review 3). CDP Fetch doesn't pause Chrome's own Reporting API uploads (`Reporting-Endpoints`/`Report-To`/NEL: `application/reports+json` POSTed within the page's first second and again ~60 s later, https only, so short runs leak too): launch with `--disable-features=Reporting,NetworkErrorLogging,DocumentReporting` joined into one switch with any names the launch already has (Chrome keeps only the last `--disable-features`; `Reporting` alone stops them), and prove it with a local https page that breaks its own report-only CSP, kept loading 72 s, beside a control run with the switch taken off (review 3, fixer 3). In such a probe each navigation-type write (a form POST, an `<a ping>` click) gets its own target frame, or the later one cancels the earlier before its request starts and that branch tests nothing; confirm each kind by its refused entry in the report (auditor). A Chrome launched detached needs the tool's handlers registered before the launch, the launch handing out its kill as soon as the process exists.
- A hidden, state-dependent part (a closed `details`) is read again whole in its shown state, elements included: under a `display: none` parent flex children aren't blockified, so a hidden flex list's links read as one words box (site-menu fixer 1).
- A "never press a form's control" guard keyed on `BUTTON`/`INPUT` misses address-less links and `role=button` elements a script wires to submit (a fixture got `POST /subscribe/`, the link recorded as the closer): guard by `closest('form')` for every tag on every press path, and, tag-independent, fail non-GET requests and main-frame navigations (CDP Fetch) while the capture presses, never counting such a press as a close (site-menu review 2). To tell which press caused a request, wait in the page's own time (`evaluate` a `setTimeout` promise), then one DevTools round trip, before counting: by the capture's clock a POST a handler sent 50 ms after its click was charged to the next press. `assembleCapture` copies `web.notes`, so a capture step after it pushes its notes into `snapshot.web.notes` itself or they are lost (fixer 2).
- A Bricks Interaction that takes `brx-open` off an Offcanvas must select open ones only (`.brx-open` in its selector): `classList.remove` of an absent class still writes the attribute, and Bricks' offcanvas MutationObserver then runs its close steps on a closed box (`brx-closing` for a tick, focus back to its last opener, the page scrolling there). Probe a page-wide click Interaction in its idle states (nothing open; after one open and close), not only while a box is open (site-menu review 2).
- A capture that presses page controls handles `Page.javascriptDialogOpening` and bounds each press: a handler calling `alert()` blocks `Runtime.evaluate` for good in headless Chrome, and a try/catch around the reading never sees it (site-menu review 1).
- **A fixture standing in for a page builder's script is written from the builder's own public code, never a plan's description.** Elementor Pro's pop-ups (PRO Elements on GitHub is the GPL build: `assets/js/elements-handlers.js` onInit/showModal/setEntranceAnimation; Elementor's `assets/lib/dialog/dialog.js`) remove every served pop-up template from the page at load, put a clean copy in the dialog on each open (shown by an inline display), take the entrance class off again on a timer and remove the copy on close: a served template can't be looked up in the live page, and a declared animation may be gone when rules are read (site-menu builder 2).
- An embed's snippet is not only its slot: `scriptsFor` (`src/web/map/snippets.ts`) adds tags from elsewhere in the page (inline scripts naming the host; for `how: host`/`frame` every script loading from it), so anything that executes a snippet checks `how` and what was added (a Meta Pixel rode along with a Facebook box). The served page comes from a separate fetch (`servedHtml`) that answers `""` when refused: a served frame reading `how: "live"` or a floating extra with a null snippet means it was empty, as in Justin's 2026-11-09 bdryswi.com capture (site-reviews review 1). The served page is parsed with scripting off, so a `<noscript><img>` in `<head>` (a tracking pixel's fallback) ends the head there and every later head tag is a child of `<body>`: a rule reading "the served children of a box" sees head scripts at body level (review 2). What a script drew beside its own tag doesn't prove the tag alone draws it (a served placeholder it replaces; a library tag plus an inline call, which draws at the call, not the tag): a bare tag pastes to run only where its box was served with no other script, style, link or template, every other served child is still there, and the drawing stands between the tag's served neighbours; else the copy (`embeds.ts` `ownPlace`, fixer 2). An importer change that makes new embeds reaches the panel's Figma route too (`src/plugin/capture.ts` → `convert`), where an embed's Code element pastes rule 2's whole snippet, tracking included: probe what both routes paste to run, not only the code method's parts (site-reviews auditor: 8 scripts and the tracking account per Code element there, still copies on main). On the panel route a captured widget's slot is one empty frame with no layers (`src/web/map/node.ts:141`), so there is no still copy to fall back on: the safe output is the empty box of its size, as no-code and php embeds already give; only the code route has a copy (panel-embed-code planner). The capture's "made by" (`src/web/read/tracker.ts`) is the innermost script file on the stack, so a rule keyed on "the file that made it" is probed two ways the repo's direct-drawing vendor fixtures hide: a CDN library a site-own script calls (the box reads as another company's), and a vendor's served bootstrap tag that injects the bundle which draws (the creating file was never served) (panel-embed-code review 1). `new Error().stack` holds only 10 frames by default, so a site frame under a deep library call is cut off and the library reads as the caller: raise `Error.stackTraceLimit` around the read and put the page's own value back (fixer 1, mutant P18). Don't tell a library from a vendor's file by what the file "does", and don't infer "this loader does nothing else": use the whole stack at creation (the file alone on it; the site's code on it) plus what the box holds (another host's loads or links → another company's; a site link or picture → the site's own), and paste a widget's tag only when its served file is alone on the stack (Justin's "Safe rule", fixer 2). "Alone on the stack" must count code with no file: V8 prints an injected inline script, `eval` and `new Function` as `<anonymous>:L:C` or `eval at … (file)`, so a served tag manager running a rule's custom code looks alone (native frames print `(<anonymous>)` with no line); probe a stack rule with the tracker injected by `Page.addScriptToEvaluateOnNewDocument`, never as an inline script, which puts the page's own address on every stack (review 3, R3-1). "This loader does nothing else", read from what a page-side tracker saw, only proves what was seen: `document.write`, `import()`, a Worker, a frame's own fetch, a WebSocket, a CSS `@import`, and anything after the read (timers, click or consent handlers) pass unseen, a vendor SDK that waits for the page's init call reads as a "library" (its launcher the site's own box), and a tag manager that calls it on `onload` becomes the pasted root; a review draws the pasted code on a fresh origin and counts hits (review 2: 8 of 8 hidden-channel roots pasted).

## What counts as shown
- Fixed boxes the design width hides (a phone-only "Call now" bar, a header's phone-only fixed bar) must be read from the ranges that show them: collecting floating boxes only from the design width's reading drops them silently. Probe floating and fixed clauses with a fixed box shown only at 767 and below and one shown only above (web-capture verifier 3, V3-F1). Build such a box from the range that shows it (the design width's range has no rect: `sizingOf` throws), and measure every window-relative test (the backdrop's half-the-window) against that range's window, or a phone-only dim layer becomes an "own" extra; compare base and head floating lists on the live homes (wave-1 fixer 12).
- Hidden is more than `display: none`: `visibility: hidden` (closed dropdowns, megamenus, popups) and screen-reader
  boxes hidden with the old `clip: rect(…)` (Bricks' `.skip-link` is 20×10 with padding, not 1×1) are not visible
  layers (web-capture review 1). But the capture reads after its freeze scrolls back to the top, so reveal-on-scroll
  content that hides itself again off screen is `visibility: hidden` then: probe a reveal that toggles both ways
  before changing what counts as shown (web-capture review 2). Bricks Interactions hide entrance content with opacity,
  not visibility (`:not(.brx-animated)[data-interaction-hidden-on-load]`, `.brx-animated[data-animation*=In]`), start
  after `setTimeout(delay)` and then wait for the box to come into view once: a scroll-through faster than the delay
  leaves every plugin `cta-motion` button below the first screen at opacity 0. Probe Bricks pages with Bricks' own
  rules from the site's `frontend-light-layer.min.css` (web-capture review 5). A Bricks Interaction's load fade-in
  can race a reader's load reading, so its trigger (load/scroll) or duration reads differently between two loads of
  the same page (web-compare fixer 4: 2 timing findings in a self-compare of the plugin-made home), so a noise-floor run that happened to read them alike mutes nothing: take as the noise file a self-compare report that holds the variation, and say so (web-compare fixer 6). The race varies in either of two fields, trigger (load → scroll) or duration (1000 → 1500): a noise key that includes the field mutes only the one its floor read (web-compare review 8). Undoing them takes
  more than one pass: Bricks arms a box (`.brx-animated` + an "In" `data-animation`) after its timers and re-arms an
  `enterView` box each time it re-enters view, so remove the marks and keep a MutationObserver on `data-animation`/`class`
  removing them again; lift `data-interaction-hidden-on-load` only when the box's own `contentLoaded`/`enterView`
  animation targets it (a hover or click overlay keeps it). Bricks' hide rules sit in `@layer bricks`, so a box's own
  opacity beats them (web-capture fixer 5). Never send `bricks/animation/end/<id>` to run chained "Animation end"
