## 3. Mechanism choice (source-backed)

| Route | Verdict |
|---|---|
| Bricks link-control key | **None exists.** The official schema `reference/bricks/link-schema.json` (2.4.3) has only `type,url,postId,newTab,rel,title,ariaLabel,lightboxId,lightboxType`. Do not invent a `download` key. |
| HTML `download` attribute via Bricks **custom attributes** (`settings._attributes`, a repeater per `reference/bricks/form-schema.json:4445`; already emitted for marquee tabindex at `emit/elements.ts:103-104`) | **Chosen.** Bricks applies custom attributes to the element's root. For a linked Button, or a Div/Block with `tag:"a"`, the root *is* the `<a>`. A documented Bricks recipe adds exactly this: Style → Attributes → name `download` on a linked Div (Meta Box + Bricks tutorial, docs.metabox.io/tutorials/create-download-preview-buttons-with-bricks). The Bricks Academy "File" element page also says a browser or external host can still open the file. |
| Valueless `download` in inline rich text | Possible (WordPress kses allows `download` on `<a>` **only valueless**; core changeset 43813 / ticket #44724), but out of scope under 3A. |
| Server `Content-Disposition: attachment` | Would force downloads for every visitor and every PDF view on the site. It is a live-site configuration change, outside the plugin. Not done (4A). |
| JavaScript fetch→blob download | Needs a Code element/signatures, fails for cross-origin without CORS, and adds script. Rejected. |

**Browser rules the plan relies on (HTML spec "follow/download the hyperlink"):**
- A same-origin `<a href=…pdf download>` is downloaded. The `target` attribute does not apply on the download path.
- A cross-origin link: browsers ignore `download` and navigate normally. With 2A, that navigation keeps `target=_blank`/`noopener`, which is today's behaviour.
- The attribute is written **valueless** (`value: ""`), so the browser uses the server's filename. It cannot be used to rename a file's type (the same reason kses only allows the valueless form).
- Task 1 must prove these rules in real Chrome before any source change. If Chrome opens an extra (even blank) tab for `download`+`target=_blank` on a same-origin PDF, the plan switches to **2B**: drop `newTab`/`rel` on download controls only. Record that switch as a ruling.

## 4. Exact general behaviour

**Download control (rule):** an element-level link whose address passes `isPdfAddress` and whose Bricks element is one Bricks itself renders as the `<a>`: `button`, or `div`/`block` carrying `tag:"a"`. This is structure and element kind only. Words, names, ids, pages, colours and URLs are never consulted. Why this is the correct general rule: such an element's whole click target has exactly one action, fetching that file, so a download is what the click means. Words inside prose are reading links (3A).

For every download control the emitted settings become:
```json
"link": { "type": "external", "url": "<unchanged>", "newTab": true, "rel": "noopener" },
"_attributes": [ { "id": "<shortId('attr:<irKey>:download')>", "name": "download", "value": "" } ]
```
- Merged with any existing attributes (a marquee loop copy's `tabindex:-1`) in a fixed order: existing marquee attributes first, then `download`. IDs stay deterministic.
- This covers Figma-linked buttons and boxes, list download buttons, row buttons with uploaded PDFs, CSV document-address PDFs, and phone copies (same emitter).

**Unchanged (explicit non-goals):**
- Inline rich-text PDF anchors keep `target="_blank" rel="noopener"` and gain no `download` (3A).
- Linked **images** and whole-element-linked text/heading elements keep pdf-new-tab output. Bricks places custom attributes on the root, which for those is not the anchor, so a `download` there would be wrong or unproven.
- Non-PDF links: byte-identical. No HEAD requests, no MIME sniffing, no filename override.
- No server, `.htaccess`, LiteSpeed or WordPress setting changes (4A). No JavaScript.
- Already-pasted pages are not repaired by Convert. Justin must re-convert and re-paste (Services).
- No promise of a specific folder, of no "Save as" prompt, or of a download for PDFs hosted on another website.

## 10. Choices made

- Mechanism: the Bricks custom-attribute `download` on download controls, not a new link-control key, not a server header, not JavaScript.
- Valueless `download` (`value: ""`), so the server filename is used, the same form WordPress kses permits.
- Element-kind scope (Button/Div/Block-as-anchor) rather than `buttonLike`/word detection. This avoids a second "is it a button" predicate that could disagree with list detection (project pitfall), and never keys on words.
- Keep `newTab`/`noopener` (2A) as the cross-origin fallback, gated by the Task 1 probe.
- pdf-new-tab's ruling "no download attribute" (HANDOFF:540-542) is reversed **only** for download controls; record this in CLAUDE.md.
