## Review 1's findings (verbatim; reviewer's verdict: findings, nothing critical or major, AC1–AC4 accepted on c574cdd)
- **R1-F1 (minor, introduced):** A present but empty `order` sent with other changes is silently accepted and ignored, though the spec says `order` lists every resulting item exactly once. Evidence: probe P1 `{parentVersion, removeItems:[test-writer], order:[]}` → 201, version 2 = [A, D], order ignored; `internal/web/pack_builder.go:202` leaves `change.Order` nil for an empty array, `internal/pack/builder.go:180` then returns next; spec `contracts/control-plane.openapi.yaml:1791-1798`; AC4 covers only `order:[]` alone (`empty_order_and_nothing_else`). Suggested: refuse a present-but-empty order with 400 INVALID_PACK (`body.Order != nil && len(*body.Order) == 0`), add `minItems: 1` to the new `order` property (new in this story, so not breaking), add an AC4 API case `empty_order_beside_a_removal` (400, nothing written). Alternative: document that an empty order counts as absent.
- **R1-F2 (minor, introduced):** The new item form's 4 KiB body bound (plan D6, GO-HTTP-002, web README "the form keeps the 4 KiB bound") has no test. Evidence: mutant R19 (`adminForm` → `adminFormLimit(w, r, 64<<10)` at `internal/web/pack_items.go:99`) survives AC4 and every other test; probe P5 shows the bound works today (5 KiB form → 400 INVALID_REQUEST). Suggested: an AC4 console case `oversized_form` posting more than 4 KiB, expecting 400 INVALID_REQUEST with nothing written (the `refused` helper).
- **R1-F3 (nit, introduced):** The `parent_version` count guard (`pack_items.go:104`) has no test. Evidence: mutant R3 survives; without the guard a missing `parent_version` gets 409 "newer version" instead of 400; probe P3: missing → 400, two values → 400. Suggested: add "no parent_version" and "two parent_version values" to AC4 `no_button_or_two_buttons` (`pack_items_test.go:752`), expecting 400 INVALID_REQUEST.
- **R1-F4 (nit, from plan D2's design):** When an `order` only rearranges the added items among themselves, the save isn't flagged `reordered`, so the audit has no `order` and `diff.added` is sorted: the record can't show the new version's order. Evidence: probe P4: parent [A], add [B, D], order [A, D, B] → 201; audit after-value has no order key; `diff.added` = [test-writer, github-mcp] sorted; `reordered()` at `builder.go:91`, audit branch `pack_builder.go:121`. Suggested (not blocking): record `order` whenever the request carried one, or note the rule in `internal/pack/README.md` for 902d's history reader.
- **R1-F5 (nit, from plan D3's decision):** Fork, Edit or Add-library-item on Pack Versions applied to a built version writes position 0, so the derived version silently drops the admin's order and lists by kind, then name. Evidence: `VersionService.create` → `Store.CreateVersion` → `insertVersionItems(..., false)` at `internal/store/postgres/pack_versions.go:66`; mutant R11 shows the store test pins this intended behaviour. Suggested (not blocking): one line in `internal/pack/README.md` saying versions derived on Pack Versions list by kind, then name.
