## How we test a story here (agreed with Justin, accepted by Christian)
- Commands: `make test` (everything, race detector), `go test ./internal/web -run <TestName> -v` (fast loop), `make check` (full CI gate: workspace, contracts-check, fmt, vet, test, lint, govulncheck, gitleaks, build), plus `bash ./scripts/test-module-add.sh`. Needs `LEORNA_TEST_DATABASE_URL` set or Postgres tests silently skip; confirm they ran with `-v`. `make check` (its `contracts-check` regenerates and restores `packages/contracts/controlplane.gen.go`) and `test-module-add.sh` (a `.module-add-test.XXXXXX/` dir joined with `go work use`) briefly write into the tree they run in, so a read-only verifier or auditor runs them in a detached copy at the same SHA; `go test` alone is safe in the story worktree, which `ac-check.sh` needs clean (901v v3 merge verifier, 2026-10-24).
- Test first, always: write the test, watch it fail for the right reason, then write the code (superpowers TDD skill).
- One subtest per acceptance criterion, named after it, in a Postgres-backed HTTP test modelled on `TestTeamsAPIWithPostgres`: throwaway schema + `ApplyMigrations`, create users (`ResolveOrCreateGoogleUser` = new tenant admin; `CreateUser` in `store.WithTenant` = member), insert session rows, set the two cookies. "UI component tests" in stories means asserting on rendered HTML; there is no component framework.
- Always include: member gets 403, wrong CSRF gets 403, unknown and other-tenant IDs get 404 (store answers not found, never forbidden), unauthenticated HTML page gives 302 to `/v1/auth/google/login`, and a tenant A vs tenant B isolation test. Store-level test covers the same boundaries without HTTP. Handler branches a real DB can't reach get a small fake repository test.
- Lessons from the review: scope HTML assertions to the element (e.g. each tile block), not whole-body `Contains`; vary fixture values so one value can't mask another; assert JSON by unmarshalling and checking the key set, not substring search; add new tables to both lists in `TestMigrationRoundTrip` and to the `resetDatabase` drop list; prove a hardened assertion can fail by temporarily mutating the code, then restore it.
- Mutation checks: scope the edit to the function under test (the same `pgErr.Code == "23505"` line exists in several store functions; a replace-first hit the wrong one). A "run it concurrently" test after the row already exists never races; force the race with an uncommitted insert in another tx and wait for `pg_stat_activity.wait_event_type='Lock'` (see `waitForLockWait` in `pack_versions_test.go`).
- Web test fixtures: `newPackFixture` (`internal/web/packs_test.go`) gives a throwaway schema, admin/member/other-tenant principals, `login`, `get`, and exposes `handler` + `pool`. `newSetupFixture` (`setup_test.go`) adds the real `provision.Service` over the mocked cloud `auditWorkflowProvider` (`cloud_audit_test.go`, `fail` toggle, returns endpoint outputs) and `connectScaleway` (stores a credential via `secret.Vault`, like the launcher). Async provisioning: poll the page or store with a 5 s deadline.
- Forced write failures: `ALTER TABLE <t> ADD CONSTRAINT <name> CHECK(false) NOT VALID`, then drop it to prove retry (on the fixture's schema-scoped pool).
- Mutations that replace a condition with `false` can leave a variable unused and break the build, which proves nothing; use a never-true comparison instead (e.g. `x == Status("never")`).
- Errors: the console returns JSON problems via `writeProblem`; only the setup wizard renders inline HTML errors (with `writeHTMLPage(w, nonce, status, page)` in `packs.go`).
- Docs claims about tests must be true as written (the README said the round-trip covered migration 14 before it did).
- OpenAPI changes: a new operation needs a stub on `roundTripServer` (`packages/contracts/roundtrip_test.go`, `var _ StrictServerInterface`) and a method on `*web.Handler` (`handler.go`, `var _ contracts.ServerInterface`). Any new enum must be a named schema, never the inline `kind: {type: string, enum: [...]}` form: both repos' contract-kind tests (`internal/web/contract_kinds_test.go`, client `application/contract_kinds_test.go`) require exactly 2 such lines (86bcm901w planner, checked 2026-10-28).

## CI secret scan scans every branch
CI checks out with `fetch-depth: 0` and runs `gitleaks git`, which scans ALL refs, so a flagged commit on anyone's branch fails every PR's "Scan repository for secrets" step. Locally `make check` only sees the branches you've fetched. To reproduce: `git fetch origin && gitleaks git --redact -v`; to check only your PR: `gitleaks git --redact --log-opts="origin/main..HEAD"`. The config is `.gitleaks.toml` from the PR's merge commit, so an allowlist only helps once it's on main. A "Re-run jobs" reuses the old merge commit; a new push is needed. First hit 2026-09-26: PR #47 failed on two fake test JWTs in Christian's PR #46 branch `feat/console-session-capture` (`internal/console/extract_test.go:66`, `internal/console/capture/capture_test.go:46`).
