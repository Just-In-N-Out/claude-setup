## How we test a story here (agreed with Justin, accepted by Christian)
- Commands: `make test` (everything, race detector), `go test ./internal/web -run <TestName> -v` (fast loop), `make check` (full CI gate: workspace, contracts-check, fmt, vet, test, lint, govulncheck, gitleaks, build), plus `bash ./scripts/test-module-add.sh`. A quick check outside `make check` must name the workspace module too: root `go build ./...`/`go vet ./...` skip `packages/contracts` (`go list ./... | grep -c packages/contracts` is 0), so add `./packages/contracts/...` (86bcm901r #99 fixer).

- Test first, always: write the test, watch it fail for the right reason, then write the code (superpowers TDD skill).
- One subtest per acceptance criterion, named after it, in a Postgres-backed HTTP test modelled on `TestTeamsAPIWithPostgres`: throwaway schema + `ApplyMigrations`, create users (`ResolveOrCreateGoogleUser` = new tenant admin; `CreateUser` in `store.WithTenant` = member), insert session rows, set the two cookies. "UI component tests" in stories means asserting on rendered HTML; there is no component framework.

- Lessons from the review: scope HTML assertions to the element (e.g. each tile block), not whole-body `Contains`; vary fixture values so one value can't mask another; assert JSON by unmarshalling and checking the key set, not substring search; add new tables to both lists in `TestMigrationRoundTrip` and to the `resetDatabase` drop list; `ApplyMigrations` checks each applied migration's sha256(up + NUL + down) on every startup, so editing an unreleased migration in place makes any database that ran the old file refuse to start ("migration N checksum mismatch"), not keep the old rule: recreate those databases (86bcm901r verifier); prove a hardened assertion can fail by temporarily mutating the code, then restore it.
- Mutation checks: scope the edit to the function under test (the same `pgErr.Code == "23505"` line exists in several store functions; a replace-first hit the wrong one). `internal/store/postgres`'s `seedBaseStore` only resets the DB and migrates, never `EnsureSeedBase`, so a mutant that lets shared seed rows into a shared-row query survives every store test; run such probes in `internal/web`, whose fixtures load the seed base (86bcm901r review-1: R1-M19 survived in store, killed by AC1 in web). Admin principals skip the team-membership check on project reads (`internal/web/projects.go:73`, also `withProject`), so an engineer-facing desktop test that mints its token for `fixture.admin` never runs the member path: mint it for `fixture.member` added to the team (86bcm901r auditor 2: AC2 used the admin token; a member probe passed and got 404 for another team's project). A "run it concurrently" test after the row already exists never races; force the race with an uncommitted insert in another tx and wait for `pg_stat_activity.wait_event_type='Lock'` (see `waitForLockWait` in `pack_versions_test.go`). Match the waiting query loosely (`LIKE '…%FOR UPDATE%'`), not by exact SQL text, and wait for the blocked goroutine on every exit (WaitGroup in the deferred rollback): an exact match reports "never waited" after a harmless SQL change, and the leaked goroutine later commits into other subtests' row counts (901w `waitForPackLineageLock`, commit `bede133`). For an advisory lock a loose poll also sees other databases and other tests' waits on the same key (advisory keys are per database, so the per-schema fixtures share them), and a delete-the-lock mutant survives by timing: run the code under test on its own pool with a unique `application_name` and poll `application_name=$1 AND datname=current_database() AND wait_event='advisory'`, creating that pool before the deferred rollback, since `pgxpool.Close` blocks (86bcm901r M3). chromedp console captures: after clicking a submit that redirects (303), Poll/Evaluate fails with "Inspected target navigated or closed (-32000)", and `WaitVisible` on an element both pages share (edit page → edit page) can match the old page. What worked first time: an `ActionFunc` loop calling `chromedp.Evaluate` every 250 ms, ignoring errors while the page navigates, until content only the new page has is there and `document.readyState == 'complete'` (up to 30 s; 901w verifier's `waitFor` in `evidence/86bcm901w/verifier/capture-main.go`). ## CI secret scan scans every branch
CI checks out with `fetch-depth: 0` and runs `gitleaks git`, which scans ALL refs, so a flagged commit on anyone's branch fails every PR's "Scan repository for secrets" step. Locally `make check` only sees the branches you've fetched. To reproduce: `git fetch origin && gitleaks git --redact -v`; to check only your PR: `gitleaks git --redact --log-opts="origin/main..HEAD"`. The config is `.gitleaks.toml` from the PR's merge commit, so an allowlist only helps once it's on main. A "Re-run jobs" reuses the old merge commit; a new push is needed. First hit 2026-09-26: PR #47 failed on two fake test JWTs in Christian's PR #46 branch `feat/console-session-capture` (`internal/console/extract_test.go:66`, `internal/console/capture/capture_test.go:46`).
